## 一個 Claude Code，49 個員工

[Claude Code Game Studios](https://github.com/Donchitos/Claude-Code-Game-Studios) 是 GitHub 上的一個開源模板，11 月 7 日看是 36,125 顆星。根據 [Build With Neej 的每週整理](https://buildwithneej.substack.com/p/5-github-repos-that-everyone-starred-this)，光是 10 月 31 日到 11 月 6 日這一週，就多了 6,685 顆。

它做的事一句話講完：把一個 Claude Code，變成一間 49 人的遊戲工作室。有總監、有部門主管、有寫程式的，還有 QA。聽起來很像在演戲，可是背後的道理，你自己叫 AI 寫程式的時候今天就用得上。

![Claude Code Game Studios 的 GitHub 頁面，右上角 36.1k 顆星，About 寫著 49 AI agents](/blog/ep092/github-repo.jpg)

## 這間工作室長什麼樣子

它分三層：

- **總監 3 個**：創意總監、技術總監、製作人。
- **部門主管 8 個**：主企劃、主程式、美術總監、音效總監、劇情總監、QA 主管、發版經理、在地化主管。
- **專家 38 個**：寫玩法的、做關卡的、管資安的、測試員都有，另外還有 Godot、Unity、Unreal 三套引擎專家。

每個角色就是一個 Markdown 檔，放在 `.claude/agents/` 底下。除了 49 個角色，還有 74 個 skill（打斜線叫出來的指令，像 `/start`、`/brainstorm`），15 個 hook，以及 14 條依資料夾套用的規則。

連模型都分好了：三個總監指定 Opus，主程式跟 15 個專家用 Sonnet，剩下 30 個沿用你現在用的模型。

![README 的 Studio Hierarchy：三層角色清單，下面寫著各層用哪個模型](/blog/ep092/github-hierarchy.jpg)

## 為什麼要拆成很多個 AI？

一個 AI 就能寫程式，幹嘛拆成 49 個？

關鍵在 context，也就是 AI 這一輪對話記得住的內容。[Claude Code 官方文件](https://code.claude.com/docs/en/sub-agents)寫得很清楚：每個 subagent 都在自己的 context window 裡跑，有自己的系統提示、自己能用的工具、自己的權限。

你把它想成開會。全公司擠在一間會議室，什麼都一起討論，講到第三個小時，大家都忘了一開始在吵什麼。分成部門各自開，最後只把結論交上來，每個人腦袋裡就只有自己的事。

拿 QA 來說，它是一個新開的 subagent，看不到前面三小時的美術討論。你交代它看什麼，它就只拿到那些。你還可以只給它讀檔的工具，它想動手改程式，也沒有那個權限。

![Claude Code Docs：Create custom subagents，說明每個 subagent 有自己的 context window、系統提示、工具與權限](/blog/ep092/docs-subagents.jpg)

## 角色一多，誰說了算？

角色一多，一定會吵架。它的做法照真實的工作室（README 的 Agent Coordination）：

1. 同一層的可以互相問意見，但不能替別的部門拍板。
2. 吵不出結果，就往上交給共同的主管：設計的事找創意總監，技術的事找技術總監。
3. 跨部門的改動，由製作人協調。
4. 每個角色只改自己範圍裡的檔案，要動別人的範圍得有人明確交辦。

這跟公司裡分權限是同一件事：寫文案的人，手上本來就沒有正式環境的鑰匙。

## 光靠說明不夠，還要自動檢查

角色說明寫得再清楚，AI 還是可能會忘。所以它另外掛了 15 個 hook。hook 是 Claude Code 在固定時間點自動跑的小程式，例如 `validate-commit.sh`：每次要 `git commit` 之前，先檢查有沒有把數值寫死、JSON 格式對不對、設計文件的段落齊不齊。

[官方的 hooks 文件](https://code.claude.com/docs/en/hooks)也寫了：在工具執行之前跑的 hook（`PreToolUse`），只要以代碼 2 結束，這個動作就會被擋下來。這一關每次都會跑，跟 AI 記不記得無關。

![Claude Code Docs：Hooks reference 的 Exit code 2 段落](/blog/ep092/docs-hooks.jpg)

還有一種是照資料夾套用的規則。寫在 `src/gameplay/` 的程式，數值要從設定檔讀；寫在 `src/networking/` 的，一切以伺服器為準。AI 改到哪個資料夾，就自動帶上那個資料夾的規矩。

## 流程開滿，結果排最後

最有意思的是作者自己做的實驗。同一份需求，用不同的嚴格程度（`modes.rigor`）各做一款遊戲，然後數一數：寫第一行程式之前，先寫了幾份文件。

| 嚴格程度 | 寫第一行程式前的文件 | 花的時間 |
| --- | ---: | ---: |
| `minimal` | 1 份（一頁的需求） | 0 分鐘 |
| `standard` | 30 份 | 58 分鐘 |

每一款都做出了能跑、有測試的遊戲。結果兩位盲測評審，再加上一場真人試玩，把 `standard` 那款排在最後。作者的結論是，多出來的 29 份文件換到可追溯，遊戲本身沒有變好玩。

![README 的 Does it produce games, or documents? 段落與 minimal、standard 對照表](/blog/ep092/github-rigor.jpg)

所以它的預設值，就是最輕的 `minimal`。我很喜歡作者把這個結果寫出來。角色跟流程都是成本，要花在真的會出事的地方。

它倒是有一件事，每個等級都照做：只要改到玩家看得到的東西，就要真的把遊戲開起來看，截一張圖存到 `production/qa/evidence/`，才算做完。

## 今天就能做的一件事

如果你已經在用 Claude Code，今天就能做一件事：在專案裡開一個 `.claude/agents/` 資料夾，先放一個審查員就好。

```markdown
---
name: reviewer
description: 改完程式後找它檢查
tools: Read, Grep, Glob
---
你只負責檢查，回報問題：
- 有沒有把密碼寫進程式
- 有沒有改到不該改的檔案
```

開頭三行是名字、什麼時候找它、能用哪些工具（官方文件說只有 `name` 跟 `description` 必填；`tools` 不寫，就會拿到全部工具）。工具只給讀檔跟搜尋，下面再用白話寫它要檢查什麼。

資料夾是新開的話，先把 Claude Code 重開一次，它才讀得到（官方文件說，已經有的資料夾裡新增或修改，幾秒內就會自動讀到）。之後每次叫 AI 改完程式，就叫這個審查員看一遍。它有自己的 context，不會被剛剛的對話帶著走；它也沒有改檔的工具，只能回報。先一個就好，真的不夠，再加第二個。

49 個員工聽起來很熱鬧，真正值得抄的就三件事：分開的 context、說清楚誰拍板、再加上自動檢查。
