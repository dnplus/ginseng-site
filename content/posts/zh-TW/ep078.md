角色坐上椅子，椅墊直接切進腿裡。這張截圖是 Codex 拍的：它自己開瀏覽器，像玩家一樣玩我做的咖啡廳 PA Cafe，把問題一張一張拍下來。這集把這陣子的開發日誌剪給大家看，順便聊聊我怎麼搭一套讓 AI 幫我測試的工作流。

## 我為什麼這麼在意驗證

- 現在叫 AI 寫程式已經很快。寫得越快，事情就越堆在後面：測試、驗證、上線，最後都卡在人身上。
- lint 檢查程式碼的寫法，unit test 一小段一小段去測，這兩種能擋掉一部分問題。大部分的 bug，要像使用者一樣把整條流程跑一遍才會冒出來，這叫 end-to-end test，我覺得是最重要的一環。
- SDD 是先把規格寫完整，再讓 AI 照規格寫程式。這個做法我一直有保留，因為規格開發到一半常常在改。我比較在意的是：每改一次，能不能馬上驗證它還是對的。
- 這點跟 Cursor 的工程師 poteto 想法很像。他的 pstack 裡有一個 create-verification-skill，專門替專案產生一份驗證用的 skill。PA Cafe 現在的驗證，照他的方法做。我之前也寫過 end-to-end test 的 skill，只是沒有他這麼有結構。

---

## PA Cafe 做到哪，為什麼是 2.5D

- 進度：認證這些基礎工程剛做完，接下來最重要的是把咖啡廳弄得更漂亮、更好玩。這陣子的測試，都圍著家具、燈光、坐姿在轉。
- 2.5D：房間跟家具是 3D，角色是一張直立的圖卡。

![PA Cafe 的起始配置畫面：房間跟家具是 3D，角色是直立的圖卡。](/blog/ep078/zh-TW-02.webp)
*PA Cafe 的起始配置畫面：房間跟家具是 3D，角色是直立的圖卡。*

- 選 2.5D 的原因：我希望大家可以上傳自己喜歡的角色。現在用 AI 生一張角色圖很簡單，要把角色做成 3D 模型，建模還是有門檻。
- 家具：原本讓 Opus 用程式碼一塊一塊拼出來。後來發現 dots 用 Blender 做的模型也不錯，我把整批換過去，一天就換完。現在店裡的 221 件家具資產，都是 dots 做的。
- 角色是平的、家具是立體的，兩邊要互動，每一種都得另外處理：坐椅子、放杯子、從桌子旁邊走過去。
- 我自己沒有做遊戲的經驗，頂多手遊玩得比較多，很多做法是照手遊的感覺去想，一邊試一邊錯，錯了就讓 Codex 再測一次。

## Codex 怎麼測：五個步驟

這套驗證 skill 像一份寫給 AI 看的操作手冊：店要怎麼開、開完怎麼檢查、怎麼像玩家一樣去點、要留哪些證據、最後怎麼收乾淨。

1. **開店（Launch）**：每次測試，Codex 都在我的電腦上開一間全新、資料是空的咖啡廳，只給這次測試用。技術上它是本機的伺服器，網址後面那組號碼（port）每次都是隨機的，所以好幾個 Codex 可以同時測，各測各的。
2. **檢查（Doctor）**：像開店前的檢查表，只看不改任何資料，確認連到的是剛開的那間店、程式是最新版。沒通過就不准開始測。
3. **操作（Drive）**：用 Playwright 打開一個全新的 Chrome，照功能清單一步一步點：建立咖啡廳、改店名、重新整理。點完再從後台把資料讀一次，確認畫面和資料對得上才算過。
4. **留證據（Evidence）**：每一步點了什麼、網路送了哪些請求、瀏覽器有沒有報錯、能把整個過程重播的紀錄，加上操作前後的截圖。失敗的結果保留，修好後重開一間店、重測一輪、留新的證據。
5. **收拾（Cleanup）**：只關掉這次自己開的店，證據留著。

規則寫得很硬：一定要真的用滑鼠、鍵盤操作，才能說畫面測過了。直接改畫面背後的資料這類捷徑都不算，截圖也要真的打開來看。沒有真的跑過的 skill 只能算草稿，這份 skill 第一次做就跑了六輪才通過。

測完的結果整理成 Notion 紀錄，每一段照同一個格式：遇到什麼問題、怎麼測、哪裡失敗、修了沒、證據在哪。畫面做好、測試通過、程式合併、正式上線，這四件事也分開寫。

## 想自己試：安裝 pstack

- Claude Code：`/plugin marketplace add cursor/plugins`，再 `/plugin install pstack@cursor-plugins`。
- Cursor：`/add-plugin pstack`。
- Codex：我也裝過，沒遇到問題。
- 第一步：在你現有的專案裡跑 create-verification-skill（Claude Code 裡的寫法是 `/pstack:create-verification-skill`）。它會先讀你的專案，找出怎麼啟動、怎麼操作、要留什麼證據，產生一份專屬的驗證 skill，交給你之前自己先跑一遍。
- 另外有一個 setup-pstack，用來設定每個角色用哪個模型。我跑過，覺得差別不大，可以先跳過。

## 家具：先擺得下

- 房間配置：把原配置和提案放在同一個鏡頭比，加了書櫃和座椅，走道還是留著。
- 商店新增 125 件家具，全部 0 代幣，原本 96 個模型保留，合計 221 件。Codex 會測分類、搜尋、領取和數量，重複按也不能把數量改壞。390 × 844 的手機尺寸另外測一次，實體手機的效能還沒測。

![家具商店（電腦版）：125 件新家具，全部 0 代幣。](/blog/ep078/zh-TW-03.webp)
*家具商店（電腦版）：125 件新家具，全部 0 代幣。*

- 桌上小物：舊版用九宮格選位置，後來改成直接拖，筆電會吸到最近的合法位置。拖到地板上會顯示放不下、彈回原位，這個拒絕也是測試要通過的一項。存檔重新整理，筆電還在桌子中央。

![磁吸拖曳：筆電吸到最近的合法桌角。](/blog/ep078/zh-TW-04.webp)
*磁吸拖曳：筆電吸到最近的合法桌角。*

![把筆電拖到沒有承載面的地板，會顯示放不下，再回到原本的位置。](/blog/ep078/zh-TW-05.webp)
*把筆電拖到沒有承載面的地板，會顯示放不下，再回到原本的位置。*

- 儲藏庫：電腦四欄、手機兩欄，可以搜尋、可以捲動。
- 音響：沒擺出來就沒有播放器，擺出來之後點模型或按 Enter 才會打開。收起來、重新整理之後，播放器不會自己跑回來。
- 吧台：七款，檯面大小都不一樣。咖啡機的正面要朝向咖啡師，咖啡師要站在機器前面才做得出咖啡，原本它朝著顧客。這裡也抓到一個 bug：逐幀動畫會把咖啡機的方向轉回去，修好之後，再轉、再拖，重新檢查。杯子、便箋和交付區也要落在檯面上。

## 光線：窗戶跟燈

- 窗戶的位置決定房間的側光，白天、黃昏、晚上連續變化。窗戶從後牆搬到左牆，光的方向跟著窗戶走；轉相機的時候，燈的位置不動。

*35 秒的實際畫面錄影：後牆窗、轉相機、換到左牆、兩面牆各一扇窗、刪掉全部的窗，最後時間從中午推到晚上十點。這是測試程式呼叫真實的畫面程式錄的，不是正式的家具拖曳流程。*

- 效能：每一格畫面要叫顯示卡畫幾次，前後幾乎一樣（117 → 117、123 → 124），陰影一直只算一張。這是在沒有顯示卡、用軟體模擬的瀏覽器裡量的，數字不能拿來說變快。
- 室內亮度有 Dim、Soft、Bright 三段，滑桿從 55% 到 145%，只有店主能調，存檔重新整理也會記得。

- 窗光重做：以前背光的窗，地上還是畫著一塊固定的窗格；新版照實際的窗面和太陽方向投影，背光就不畫了。
- 逐盞燈：十五款燈都有自己的開關，同一時間最多四盞打局部光，其他燈罩照樣發亮。佈置模式只選取、不切換，收進倉庫再擺回來，重新整理之後，原本開著的燈還是開著。

## 坐姿：做了三個版本

- 問題：椅子是 3D 模型，角色是一張圖卡，圖卡沒有往前伸的腿，所以椅墊會直接穿過去。
- 坐姿圖集用 dots 的參考圖生成。我要的是 1024 的四乘四，實際生出來是 1254，這種尺寸差，匯入前就要處理。
- 第二版：把腿部網格往前推，椅墊擋住了，靴子卻被拉變形。穿模的數字變好看，角色走樣了，這版直接否決。
- 第三版：圖卡保持原樣，只調腿部的遮擋深度，告訴電腦腿比較靠前、椅墊要畫在腿後面。顏色、輪廓都沒動，算是 2.5D 的遮擋近似。

## 互動：拒絕也要測

- 四種互動：坐下、去吧台拿杯子、對家具做反應、自訂動作。每一種都要有走得進去、也出得來的路。
- 路不通就拒絕：桌子底下空間不夠，角色就不坐；吧台入口被擋住，就不去拿杯子。拒絕的結果也要跟伺服器的判斷對得上。

- Codex 留下的幾個真失敗，修好後紀錄都保留：重選同一張圖時，取消的動作一路往上傳，把整個設定視窗關掉；首頁載入時，把整個 3D 場景也拉進來；後台的家具配置已經改了，畫面卻停在舊的；測試自己檢查的條件寫錯。
- 所以我覺得，驗證的方法本身，也要被驗證。
- 本機結果：206 個測試檔、2,492 個測試通過，typecheck 和 lint 也通過。截至 10 月 17 日，家具商店（PR #181）和起始配置（PR #187）已經合併；窗光、亮度、逐盞燈的 PR 還沒合併。以上都是本機測試，正式部署還沒確認。

## 我現在的做法

1. 給 AI 一個能自己開、自己關、可以同時跑好幾個的環境。
2. 講清楚什麼才算通過：真的點過，截圖真的看過。
3. 證據一定要留，失敗也要留。
4. 最後一關留給人：好不好看、自不自然，還是我自己來看。
