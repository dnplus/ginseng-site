現在跟 AI 講一聲，就能做出網站和小工具，做完以後下一個問題是：放在哪裡，別人才用得到？Zeabur、Railway 這類平台，承接的就是這種需求。十月這兩家平台相繼出事，我重新想了一遍「平台包起來的東西，到底包到哪裡」。這篇整理影片裡講的幾件事：兩起事件的官方說法、服務條款寫了什麼、我自己為什麼選 Cloudflare、PHP 漏洞出來時該先查什麼，還有我怎麼用 RSS 加 Agent 追這類公告。

---

## 寫得出來之後，還得部署

![](/blog/ep081/zh-TW-01.webp)

- 我自己做的 PA Cafe，十月十五號到二十二號這一週，合併了 276 個 PR，主分支有 284 個 commit，改了 1,669 個檔案，發了 15 個版本。（圖為 GitHub Pulse 頁面，裁掉網址列）

![](/blog/ep081/zh-TW-02.webp)

- 每個 PR、每次發版，GitHub Actions 都要跑一輪。我用 GitHub Pro，私有 repository 每月有 3,000 分鐘，這個月還剩十天就全部用完，用量條整條紅色。（圖為 GitHub 計費頁，只裁 GitHub Pro 與 Actions minutes 用量）
- 我自己部署靠 GitHub Actions：程式推上去，照寫好的步驟測試、打包、部署。Zeabur、Railway 幫你包起來的，很大一部分就是這段流程。對剛開始 vibe coding、連 Git 都還在摸的人，自己寫 Actions 門檻更高，所以我完全理解這類平台為什麼吸引人。
- 程式寫得越快，後面的測試、部署、維運、資安就越多。GitHub 十月的工程文章提到，九月 GitHub Actions 跑了 32 億次，是一年前的四倍多；Anthropic 內部每天合併的程式變更，從五月約 2,500 個到九月超過 30,000 個，最後自己做了版本控制系統 Scion。
- 平台把一堆維運步驟收成幾個按鈕，這個價值是真的。我想問的是：畫面上只剩按鈕時，資料、第三方金鑰、出事後的處理，是不是都有人照顧？期待和平台實際做到的範圍之間，可能有落差。

## 出事以後，誰來處理？

![](/blog/ep081/zh-TW-03.webp)

- Zeabur 十月的初步報告寫到，平台資料庫裡有 3,218,965 筆環境變數被讀取。（圖源：Zeabur 官方初步報告）
- 環境變數裡可能放著資料庫密碼、雲端服務金鑰和呼叫 AI 的 API key，影響可能延伸到你接進來的其他服務。Zeabur 的報告說對方主要在找 API 金鑰，特別是 AI 服務的金鑰；Railway 的公告也提到最近有一連串攻擊鎖定平台公司，目的是攻進 AI 推論服務商。

![](/blog/ep081/zh-TW-04.webp)

- Zeabur 的處置指南有一句：改平台上的環境變數，不會替你改掉資料庫裡的密碼。要換密碼，得去資料庫修改，再讓程式用新的密碼。只改一邊，可能舊密碼還能用，也可能自己的服務先連不上。（圖源：Zeabur 官方初步報告，Shared cluster users 段）

![](/blog/ep081/zh-TW-05.webp)

- Railway 的公告說，儲存客戶環境變數的系統出現異常，第三方可能存取到加密資料，其中一部分取得了解密後的內容。Railway 通知了上游供應商撤銷金鑰，同時要求使用者更換憑證、檢查紀錄。（圖源：Railway 官方 Security Disclosure）
- 照公告換金鑰的人遇到的狀況很具體：Railway 有用戶把金鑰全換了，但平台部署還暫停中，新設定上不去，服務直接掛了。Hacker News 上也有人說，幸好事先設了花費上限，金鑰被盜用一天就撞到上限停下來。這類設定平常沒感覺，出事那天就派上用場。

![](/blog/ep081/zh-TW-06.webp)

- 我翻了兩家的服務條款：服務按現狀提供，賠償總額有上限，是 100 美元，或你過去 12 個月付給平台的錢。Railway 的條款寫明取比較高的那個，Zeabur 的條款只列了這兩項、沒寫取高者。資料遺失這類損害，兩家條款都寫明排除在外。（圖為 Railway 服務條款責任上限條文）
- 條款之外，Zeabur 這次公開說，第三方服務因此多收的錢，可以開工單申請補償，官方會核對用量與帳單。Railway 這次有沒有補償，我目前查不到公開說明。我把條款當成最低保障，平台另外做的事看當下的公告。

![](/blog/ep081/zh-TW-07.webp)

- Zeabur 後來宣布平台將在 12 月 31 日停止營運，用戶除了換金鑰、改密碼，還得在年底前把服務搬走。有用戶說自己是在 Threads 看到消息才知道，沒有收到信，官方後來也出來道歉。（圖源：Zeabur 停止營運公告）
- 所以我看這類平台，會問四件事：資料跟金鑰放在哪裡、出事怎麼通知我、我要停掉某個連線有沒有地方操作、明天不能用了資料拿不拿得出來。

## 我為什麼選 Cloudflare

- 我工作上經手過不少國際產品，看服務習慣往後多看一點：它怎麼運作，哪些事交給平台，哪些要自己處理。PA Cafe（我叫它 PA 小屋，每個 AI Agent 各有一間小屋）選的是 Cloudflare。Cloudflare 從 CDN、網路服務這條路走過來，長期做這些事，會影響我對它的信任。
- PA 小屋目前文件記錄的架構：用 Workers 跑服務，每間小屋有自己的 SQLite Durable Object，再搭配 R2。Workers 是跑程式的地方，Durable Object 可以想成每間小屋自己的小資料庫，R2 放檔案。
- 跟租一台主機自己管容器和資料庫不同，我不用照顧同一套主機系統，但應用程式還是我寫的。請求被送進哪一間小屋、這個 Agent 有沒有權限讀，仍然由我的程式確認。
- Cloudflare 的產品多，對一般人不一定比較好上手。平台包得越完整越容易開始；自己理解更多組成，調整空間可能多一些，也得多花時間。

![](/blog/ep081/zh-TW-08.webp)

- 資安攻防有點像矛跟盾，我不期待有一套系統永遠攻不進去，所以我看四件事：平常有沒有做好防護、出事多久能發現、能不能限制影響、資料能不能救回來。（圖為 Zeabur 初步報告的時間線）
- 拿「偵測」看 Zeabur 這次的時間線：攻擊者第一次用內部金鑰登入是 10 月 14 日早上，平台開始調查已是隔天晚上，中間約 36 小時沒有任何告警，是用戶回報異常才發現。這段時間裡，對方讀完共享叢集的設定，還進到用戶的資料庫容器下指令。
- 所以我用防禦縱深來想。我的看法是，AI 讓發動攻擊越來越便宜，無差別掃描會變多；我想，攻擊者花在每個目標上的時間和 token 總會有上限。花費上限、金鑰權限、異常告警，每多一層就拖慢對方、拉高成本。像剝洋蔥，你比別人多一層，對方可能就轉去找更好打的目標。

## PHP 漏洞與持續維運

![](/blog/ep081/zh-TW-09.webp)

- PHP Foundation 在 10 月 21 日發布修補，兩個漏洞（CVE-2026-109618、CVE-2026-109619）在特定條件下，可能讓沒有登入的攻擊者在伺服器上執行程式碼。（圖源：PHP Foundation 公告）這是軟體漏洞公告，和前面兩起平台事件分開看。
- 看到公告，第一個問題都一樣：我的東西有沒有受到影響，我現在要做什麼？程式大部分由 AI 寫的話，要先知道它用了哪些東西。至少查你用的產品和執行環境有沒有這個元件、版本是什麼。資訊不夠，就先把缺的找出來，再核對供應商公告，等確認後才動正式環境。
- AI 加快了搜尋、寫程式和反覆嘗試，攻擊者也能用。防守如果每則公告都靠人追，接的服務越多要顧的越多。我在想的是：程式收集、AI 判讀、人工確認，把人的時間留給真正需要確認的地方。

## PA 小屋 RSS＋Grok Bot

![](/blog/ep081/zh-TW-10.webp)

- PA 小屋 RSS 外掛的外部來源畫面：每 30 分鐘檢查一次，首次檢查不匯入舊文章，並預覽來源最近的文章。預覽的三個標題是 Railway Blog 2026-10-22 的文章。
- 我之前請 xAI 的 Grok Bot 定時去看各來源有沒有新消息，一直很猶豫：半小時一次嫌慢，十分鐘一次又常常看完只回報「沒有更新」。間隔拉長怕錯過，縮短又多很多次空跑。
- PA 小屋最近加了 RSS feed 外掛。RSS 是很多網站提供的更新清單，有新文章就多一筆。目前外掛會定期檢查來源，把新文章安靜記錄到來源的最近事件，不會自動叫醒住民。我希望的工作方式是：比對新項目交給程式，沒有新東西就停在這裡，有新內容才往後交給 AI。我想省的是沒消息也把 AI 叫起來的工作。
- RSS 通常由工具定期去檢查，來源另外支援推送時是另一種接法。我希望收到新文章後，先去重、篩掉明顯無關的來源、把幾條更新合在一起再判讀；資安公告這類要快點確認的，跟一般產品新聞分開處理。
- 以 PHP 這件事為例，我希望 Grok Bot 先看官方資料，再對照我提供的服務清單：有沒有用到、版本有沒有受影響、現在能不能確認，缺部署資訊就列出缺什麼，最後給我該處理的事項。
- 我希望 Agent 讀到的外部文章，就算裡面寫了操作指令，也要等我授權才算數。流程是：收件、核對官方、確認影響、授權操作、驗證。動手只在事先允許的範圍內做，完成後驗證服務。

## 最低限度的判斷能力

- 在這個時代，做產品用不著先變成工程師。至少要知道資料跟金鑰交給誰、出事去哪裡確認、必要時能不能停用連線和拿回資料。這些不一定都要自己動手，AI 也能幫忙，只是要留著判斷和確認的能力，才知道它給的答案是在解決問題，還是只是聽起來很完整。
- 我選 Cloudflare、做 PA 小屋也是這個道理。部署可以交給平台，消息可以交給程式收，判讀可以請 Agent 幫忙；要交出去多少、什麼時候自己確認，這些選擇還是我的。AI 省下來的時間，我希望也留一點給理解自己正在用的東西。
