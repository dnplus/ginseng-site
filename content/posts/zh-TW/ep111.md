## 網站做好了，一上線資料卻亂掉

你用 AI 花一個下午做出一間咖啡店的預約跟集點網站，客人能點餐，也能累積點數。丟給朋友玩就出事了：

- 客人換支手機，點數歸零。
- 有人打開瀏覽器，就把分數改到九萬九。

更頭痛的是第二版要升級。你想幫會員表加一個生日欄位，新程式推上去，原本存好的舊資料直接整個打不開。AI 寫畫面很快，但它常把介面、規則跟存檔擠在同一個地方，沒分清楚誰該管什麼。

這集是小屋技術白話課第六集。前一集講完測試與驗證，這集把資料的底層接起來。教材是 PA Cafe 小屋在 Cloudflare 上線的設定檔跟資料庫遷移程式，我直接拆開來講每份資料該放哪裡。

這篇的順序是：

1. 用同一間咖啡店看懂四個角色的分工
2. 為什麼算分跟權限要交給後端
3. 放前端之前要檢查什麼，包含 KKday 事件，以及 Cloudflare Pages 對照 Workers 的選法
4. 改欄位怎麼做到不炸舊資料
5. 回到小屋的真實設定對照一遍

## 前端、後端、資料庫怎麼分工

把軟體想成一間咖啡店，有四個固定角色：

| 咖啡店裡的位置 | 軟體裡的角色 | 負責什麼 |
| --- | --- | --- |
| 大廳桌上的點餐平板 | 前端 | 看得到、點得到的畫面，跑在客人的瀏覽器裡 |
| 櫃檯裡核對點單的店員 | 後端 | 驗證身分、檢查權限、計算點數與價格 |
| 鎖在後台保險箱的總帳本 | 資料庫 | 整齊的文字、數字、時間，一筆一筆寫進表格 |
| 堆大型貨物的倉庫貨架 | 物件儲存 | 圖片、音檔、影片這類大檔案 |

四個位置各司其職，整間店才不會亂套。

### 前端：整包程式都在客人手上

大廳那台平板就是前端。客人打開網站，手機或電腦瀏覽器裡所有看得到、點得到的按鈕、動畫跟表單，全部算前端。重點在於：網頁載入那一刻，前端的程式碼會整包傳到客人的瀏覽器裡執行。

AI 做第一版原型時，最常把資料直接寫進瀏覽器的 localStorage。你可以把它想成夾在客人手機殼裡的一張紙條：同一台手機重整網頁，字還在；客人一換手機、換瀏覽器或清掉網站資料，這張紙條就從世界消失。

![MDN 文件說明 localStorage 的資料會跨瀏覽器工作階段保存，但只存在這個瀏覽器裡](/blog/ep111/mdn-localstorage.png)

*MDN 對 Window.localStorage 的說明：資料存在使用者自己的瀏覽器，換一台就讀不到。*

### 後端：櫃檯的店員

收單算帳的店員就是後端。後端程式跑在你自己租的雲端伺服器上，負責驗證誰登入、檢查能不能執行動作、計算點數跟價格。客人只能從窗口送出請求，碰不到櫃檯裡面的規則跟帳房鑰匙。

剛學寫後端很容易想直接把點數存在程式的陣列或變數裡。但現代的無伺服器平台像 Workers，會隨時重啟，也會同時開出好幾台分身應付流量。存在程式記憶體裡的資料，分身一換或重啟就一起清空，所以持久的狀態一定要寫進外面的資料庫。

### 資料庫：總帳本

幾月幾號哪位客人訂了位、目前剩幾點、哪一筆消費換了幾點，都照固定格式一筆一筆寫進資料庫的表格。不管客人換幾支手機，只要登入同一個帳號，讀出來的都是同一份帳本。

### 物件儲存：倉庫貨架

物件儲存常見的有 AWS S3 或 Cloudflare R2。資料庫專心記文字、數字和時間這類整齊的帳目；客人上傳的頭像、照片、音檔或影片丟進倉庫，帳本裡只記它的編號跟取件網址。

### 一張對照表收尾

- 暫時性的介面草稿：留在瀏覽器本機
- 交易帳本、點數、會員資料：存進資料庫
- 第三方金鑰、驗分與權限判斷：鎖在後端
- 圖片、語音、大檔案：交給物件儲存

## 為什麼分數跟權限要交給後端

回到開頭的問題：為什麼客人換支手機點數就歸零，還有人打開瀏覽器就把分數改到九萬九？

答案很直接。點數只寫進客人的瀏覽器抽屜，換台機器就讀不到；算分跟存檔的程式都在前端跑，客人自己在瀏覽器裡就能改數字。

每個現代瀏覽器都有開發者工具，電腦上按一下 F12 就打得開。客人用它能看到網頁送去後端的每一個請求、直接改畫面上的數字、修改存放在瀏覽器的數值，甚至自己寫一段請求打給你的伺服器。

### 真例子：BARISTA BLAST 的門票

我們幫小屋做了一款網頁遊戲 BARISTA BLAST，它的算分流程是這樣：

1. 剛開局時，後端先發一張門票給瀏覽器。門票裡寫明遊戲規則版本、地圖隨機種子、小屋編號跟發票時間，再用只有伺服器知道的密鑰做 HMAC 簽章。
2. 玩家飛完送出成績時，後端只讀門票和按鍵紀錄，照當時的規則自己重跑一遍，算出真實分數。
3. 後端還會擋掉三種送件：超過七天的舊票、比遊戲秒數還快的作弊時間、重複送出的票。

### 金鑰與付費判斷也守同一條邊界

第三方 API 金鑰、扣款邏輯、判斷這個人屬於哪個方案，全部留在後端執行。金鑰只要打包進前端，就等於貼在店門口，誰打開原始碼都抄得走。

### 最容易漏的一關：這筆資料是你的嗎？

金鑰留在後端之後，還有一關最容易漏。每個請求進到後端，都要先驗證你是誰，再檢查這筆資料屬於哪個人。少了這一步，客人只要把網址裡的編號改成別人的，就能讀到別人的訂單。

這就是 OWASP 2025 年版排第一的權限控管失效（Broken Access Control）。OWASP 的統計寫到，受測的應用程式百分之百都驗出這類問題。

![OWASP Top 10:2025 A01 頁面，說明受測應用程式 100% 都有某種形式的權限控管問題](/blog/ep111/owasp-a01.png)

*OWASP Top 10:2025 的 A01：權限控管失效排第一，受測應用程式 100% 驗出這類問題。*

### 那乾脆全部交給後端算？

技術上行得通，代價有兩個：

- **負擔**：前端的程式跑在客人自己的手機跟電腦上，一千個客人就有一千台機器幫你分擔。全部搬回後端，每一次點擊都要你的伺服器出力，流量一來，帳單跟著漲。
- **延遲**：每個動作都要繞一趟網路才有結果，客人按下按鈕，要等一下畫面才動。

所以分界看一個問題：這個結果被改掉，會不會有人吃虧？

- 會，就放後端：點數、價格、權限。
- 只影響客人自己眼前的畫面，就留在前端：動畫、排序、表單填錯的即時提示。反應快，也不佔你的伺服器。

BARISTA BLAST 兩邊都用。遊戲畫面在瀏覽器裡跑，手感才跟得上；成績送出後，後端再重算一次才算數。

## 放前端要顧什麼：KKday 到 CF Workers

### KKday 夥伴百科事件

講到「資料到底能不能放前端」，可以回頭看第 104 集提過的 KKday 夥伴百科事件。新聞報導指出，這個給合作夥伴看的網頁，把近二十八天的成交量、客單價與毛利率放進了公開的前端跟 GitHub。區塊勢的影片也提到，網友保存的網頁副本原始碼裡，甚至留著「不要寫出客單金額」的註解。報導沒有證據顯示消費者個資外流，商品營運數據本身就屬於商業機密。

![聯合新聞網報導標題：業績裸奔？旅遊網站商品數據全公開](/blog/ep111/udn-kkday.png)

*聯合新聞網 2026-11-16 的報導標題：商品數據全公開。*

會出事的原因很單純：所有送進前端的網頁檔案、腳本跟內嵌資料，從網頁打開那一秒起就完整交到訪客電腦裡。就算畫面上用樣式藏起來、或只在註解寫一句提醒自己，按右鍵檢視原始碼，或看開發者工具的網路回應，全部看得到。

### 資料丟給前端之前的三關

1. **這份頁面是給誰看的？** 夥伴頁或內部報表，一定要在後端驗過身分。只藏網址擋不住外人。
2. **部署的倉庫是公開的嗎？** GitHub Pages 免費方案就規定倉庫必須公開，檔案刪掉也會留在版本紀錄裡。
3. **不該外流的欄位，在後端先過濾掉再回傳。**

### 靜態還是動態，決定部署方式

這條邊界剛好帶出部署方式的選擇：

- 部落格、公司形象頁、活動介紹這種每個人看到都一樣的內容，可以直接做成純靜態檔案，放在邊緣節點快速送出。
- 只要牽涉會員登入、後台帳本、私有數據過濾或 API 密鑰，就需要一顆後端程式在前面接單。

### GitHub Pages：純靜態託管

區塊勢的影片指出，KKday 夥伴百科架在 GitHub Pages 上。它是 GitHub 內建的純靜態託管，把網頁推上倉庫就生出公開網址。照官方文件，它沒辦法執行 Node 或 Python 這類後端程式，免費方案還規定倉庫須公開，一要登入驗證就得換平台。

![GitHub Docs 的 About GitHub Pages：靜態網站託管，直接發佈 HTML、CSS、JS](/blog/ep111/github-pages-about.png)

*GitHub Docs：GitHub Pages 是靜態網站託管服務，直接從倉庫發佈 HTML、CSS 與 JavaScript。*

### 為什麼用 Cloudflare 當範例

能接後端的雲端平台很多，這集用 Cloudflare 有兩個原因：

- PA Cafe 小屋從前端、API、資料庫到圖片儲存全跑在 Cloudflare 上，等一下能直接打開設定檔對照。
- 工程師常叫它「賽博菩薩」：靜態請求免費不限量，Workers 免費版每天十萬次請求，R2 零出口費，小專案幾乎不用花錢。

![Cloudflare Workers Pricing 頁面，免費方案每天 100,000 次請求](/blog/ep111/cf-workers-pricing.png)

*Cloudflare Docs：Workers 免費方案每天 100,000 次請求。*

### Cloudflare Pages：最早的靜態前端託管

在 Cloudflare 生態裡，最早專為靜態前端跟 Jamstack 設計的託管服務叫 Cloudflare Pages。連上 Git 倉庫，每次推送就自動建置部署，靜態請求免費不限量，免費方案每月提供五百次建置。想加輕量 API，再透過資料夾慣例掛上 Pages Functions。

![Cloudflare Pages Limits，免費方案每月 500 次建置](/blog/ep111/cf-pages-limits.png)

*Cloudflare Docs：Pages 免費方案每月 500 次建置。*

### Workers Static Assets：靜態與後端合在同一層

近年 Cloudflare 推出 Workers Static Assets，把靜態資源託管跟完整的 Worker 後端合在同一層。Cloudflare 官方的遷移文件寫得很明確：新建專案直接從 Workers 開始；既有的 Pages 站點繼續維護，沒有急迫的搬遷需求，但未來所有新功能與能力都會優先上在 Workers。

![Cloudflare 遷移文件：Workers 的功能範圍比 Pages 廣](/blog/ep111/cf-migrate-pages.png)

*Cloudflare Docs：從 Pages 遷移到 Workers 的說明，標出 Workers 的功能範圍比 Pages 廣。*

兩者的實際差別有三點：

1. Workers 用單一設定檔，同時管前端資源與後端程式。
2. Workers 原生直連 Durable Objects 帳本、定時排程 Cron、佇列與觀測紀錄，不必另外串別台伺服器。
3. 建置配額上，Pages 算每月五百次建置，Workers Builds 提供每月三千分鐘建置時間，靜態請求同樣免費無限。

### run_worker_first：誰先經過後端

同一組網站裡，誰該經過後端檢查，誰該直接送出靜態檔？Workers Static Assets 預設先找靜態檔，命中就直接從快取免費送回，找不到才叫醒 Worker。想讓後端先擋身分或處理 API，就在設定裡指定 `run_worker_first` 路徑清單，精準決定哪些網址先進 Worker 把關。

拿 PA Cafe 的 wrangler 設定檔實際看：第 17 行同時綁了編譯好的靜態目錄 ASSETS，也列了 `run_worker_first`，先讓請求走進 Worker，再用驚嘆號排除首頁、圖示、字型跟圖片資料夾。結果是公開的美編圖檔免費高速直出，帶權限檢查的房間資料與 API，每一筆都經過 Worker 驗證。

### 實務選法

- 單純做作品集、靜態活動頁或部落格，用純靜態託管已經夠用。
- 需要登入、改分數、讀私有夥伴資料或加排程任務的應用程式，從第一天就選 Cloudflare Workers 配靜態資源，才不會等網站長大後，才辛苦拆開前後端重新改寫。

## 改個欄位舊資料為什麼會炸

資料安全放進資料庫之後，第二個大魔王接著上場。

你的咖啡店網站跑了兩個禮拜，累積五百位會員。今天想加兩個新欄位：會員生日、飲料甜度偏好。程式碼寫完直接推上線，舊會員一登入，畫面跳出紅字錯誤，整個卡死。

### Schema：帳本每一欄的規格表

會炸掉，是因為資料庫有嚴格的格式定義，叫 Schema。白話說就是帳本每一欄的規格表：哪一欄叫電話、哪一欄只能填整數、哪一欄規定不能留白，都寫死在規格表裡。程式照著新規格去讀還沒補上欄位的舊表格，兩邊對不上，當場報錯。

### SQL 欄位還是 JSON 文件

寫表時還會碰到一個選擇：欄位要拆成整齊的 SQL 關聯欄位，還是整包塞成彈性的 JSON 文件？經驗法則很簡單：

- 需要對帳、排序、設唯一索引的資料，像錢包餘額、會員電話，拆成 SQL 固定欄位。
- 經常變動的小設定，可以留一欄 JSON。

PA Cafe 的表格就混用這兩種欄位，兼顧彈性跟查詢速度。

### Migration：給舊帳本換頁

解決的流程叫資料庫遷移，英文是 Migration。把加欄位、建索引、補預設值的 SQL 指令寫成一份有編號的腳本，上線時依序跑一次，並且記下這份腳本已經跑過，下次不再重複執行。

老手加欄位通常走三步：

1. 先新增允許留空、或帶預設值的新欄位，讓舊資料照樣活著。
2. 把程式換成讀寫都相容新舊欄位，同時慢慢把舊資料補齊。
3. 確認舊版程式全都退場，最後才拿掉舊欄位，或加上必填限制。

### 改表前先問：會炸到哪裡？

真的動手改表之前，我會先叫 bot 跑 pstack 的另一個技能 blast-radius，問它：在小屋的 tasks 表加一個新欄位，會炸到哪裡？

它回說，只要新欄位可以留空或有預設值，現有的寫入就不會壞，因為每一條寫進 tasks 的 SQL 都寫明了欄位名稱。最可能出事的，是新欄位跟原本存的 JSON 不同步。它還順手點出四個自己建表的測試，會跟著壞。

### 最危險的動作

最容易讓線上服務瞬間斷線的，是直接對著正在使用的表格把欄位改名，或整欄刪掉。在部署切換的那幾分鐘裡，舊版網頁或舊版伺服器可能還在跑，欄位名稱一變，請求送進來立刻噴錯。改用「先增、再搬、最後拆」的節奏，兩版就能平順交接。

### 測試站與備份

這裡接上白話課第四集的測試站。測試站跟正式站一定要綁各自獨立的資料庫。每次寫好遷移腳本：

1. 先在測試站灌進幾筆模擬的舊資料，跑過一輪。
2. 幫正式資料庫做完快照備份。
3. 再推進正式環境。

### 退路：舊版看得懂新表嗎？

上線之前還要多想一步退路。萬一新版程式跑十分鐘發現嚴重錯誤，必須退回上一版，舊版程式能不能看懂剛改過的表格？只要確保新加的欄位允許留空、也不立刻刪掉舊欄位，舊版程式就能直接降版接手，不必急著手動回滾整包資料庫。

## 拿 PA Cafe 小屋看真實分層

口說無憑，直接打開 PA Cafe 的 wrangler 設定檔看真架構：

- 最外層是編譯好的 React 前端網頁。
- 動態請求跟 API 進來，第一關先進 Cloudflare Workers 後端驗證身分。
- 資料存進 Durable Objects，大檔案送去名叫 MEDIA 的 R2 儲存桶。

### Durable Objects：每間小屋一份 SQLite

Durable Objects 有個很特別的設計：它會在雲端幫每一間小屋各自配一間專屬房間，房間裡直接附帶一份獨立的 SQLite 資料庫。設定檔裡宣告了 House、Directory 跟 InboundRegistry 三個 SQLite 類別，同一間小屋的任務跟扣點，都在自己房裡依序處理，不會跟別間打架。

### 資料表的分工

- 每一間 House 裡有管理點數餘額的 `house_wallet`、記收支明細的 `economy_ledger`、存派工單的 `tasks`。
- 跨小屋共用的 Directory，另外管全站遊戲排行榜 `blast_scores` 跟用過的門票紀錄 `blast_used`。

### localStorage 到底放了什麼

PA Cafe 裡真的有寫瀏覽器的 localStorage 嗎？我叫 bot 用 pstack 的 teach 直接去問小屋。它說有，但只放跟這台瀏覽器有關的小偏好，像語言與時區、音樂音量、畫質。點數跟任務都不在瀏覽器，存在每間小屋自己的 Durable Object SQLite 裡。所以客人就算清掉快取，點數跟任務也毫髮無傷。

### 改表不炸的實作

- `schema-meta` 檔案記住目前資料庫已經來到第 22 版，最低相容讀取版是第 21 版。
- `store-migrations` 在加欄位前，先用 `PRAGMA table_info` 檢查欄位存不存在。
- 做狀態遷移時，先寫進備份表，再用交易包起來。
- 最後寫進 `store_migrations`，確保只跑一次。

### 大檔案分流

住民大頭貼、客服語音檔，還有 BARISTA BLAST 分享戰績用的帳單圖片，通通存進 Cloudflare R2 的儲存桶，SQLite 資料庫裡只記短短的檔名鑰匙。照官方定價，R2 讀寫之外的流量出口完全免費，也就不會把 SQLite 帳本撐爆。
