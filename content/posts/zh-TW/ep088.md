## vibe coding 第一個大魔王

你想用 AI 做一個自己的東西，像店裡的預約頁。下載 Codex、登入，第一個畫面就問你：要選哪個專案資料夾？好不容易開始了，AI 又一直跟你講 commit、branch、push。

這就是 vibe coding 的第一個大魔王，Git。

### 為什麼開這個系列

我發現大家對 AI 的認知，越來越兩極。幾個月前，很多人還分不清 Claude 跟 Claude Code。有人問我，你的 ChatGPT 怎麼跟我的不一樣？Codex 是什麼，能吃嗎？聊天機器人跟 AI agent，又差在哪？

這些問題，我之前發過不少影片講。這個系列換個做法：從你怎麼跟你的 bot 學習開始，一步一步，補上 AI 時代該有的能力。

現在也有很多人想學 AI 寫程式，第一個念頭是去買課、上課。我自己覺得沒什麼必要。一門課的錢，拿去訂 AI，夠你用好幾個月。而且訂了之後，它每天都在旁邊，隨時可以問。

老實說，我也不太會做那種一步一步帶你操作的課，因為我不知道你卡在哪。每個人想做的東西不一樣，卡住的地方也不一樣。我照我的順序講，很可能剛好跳過你卡的那一步。

最清楚你卡在哪的，是你自己，還有正在幫你寫程式的那個 AI。所以這個系列，示範怎麼用你已經付錢的訂閱來學：

1. 卡住了就問它。
2. 聽不懂就叫它換個說法。
3. 再叫它拿你自己的專案舉例。

我自己做的 PA Cafe 小屋，寫程式、做驗收的都是 bot。從 10 月 10 日開始，到現在合併了 681 個 PR。這個系列就拿小屋當教材，從一個沒寫過程式的人會卡住的地方開始，把這些詞一個一個翻成人話。

### 用 pstack 當工具

做法是用 pstack。它是 Cursor 的工程師 poteto 公開的一包技能，他也是 React 核心團隊的成員。他把自己每天寫程式用的方法，整理成一個一個指令，裝在 Cursor、Claude Code 上就能用。安裝的時候，也是從 GitHub 抓下來的。

怎麼裝？最簡單的方法，是叫你的 AI 幫你裝。在 Claude Code 裡貼這一句：

```text
幫我裝 pstack，它在 GitHub 的 cursor/plugins
```

它會自己跑安裝指令，大概像這樣：

```bash
claude plugin marketplace add cursor/plugins
claude plugin install pstack@cursor-plugins
```

裝好之後開一個新對話，打 `/pstack:teach`，就能用了。用 Cursor 的話，打 `/add-plugin pstack` 就好。

這包技能很多是給工程師用的，像派好幾隻 AI 同時做事、叫不同的模型互相挑錯。裡面也有幾招，特別適合沒寫過程式的人：

| 指令 | 做什麼 |
| --- | --- |
| `how` | 講程式怎麼運作 |
| `why` | 去翻紀錄，找當初為什麼這樣做 |
| `bro` | 把 AI 剛剛那段話翻成白話 |
| `poteto-help` | 不知道該用哪一招，就問它 |
| `teach` | 把 how 跟 why 一起跑，最後用白話講給你聽 |

這系列最常用的一招是 `teach`。它先讀程式，看它怎麼運作。再翻 commit、PR 這些紀錄，找當初為什麼這樣做。最後用白話講給你聽。

所以整個系列都會繞著 pstack 的用法走。每講一個詞，我就叫 bot 用 teach 跑一次。你回家用自己的訂閱、自己的專案，照樣問一次。

問 teach 有個小技巧：問題要帶上你的專案，像「用小屋的程式解釋 PR 是什麼」。它就會去翻真的紀錄，舉你看得懂的例子。講完還會給你幾個可以再追問的方向，想聽哪個再接著問。

### 地圖：SDLC

工程師做軟體，有一套流程叫 SDLC，中文是軟體開發生命週期。大致分六步：規劃要做什麼、設計怎麼做、寫程式、測試、部署上線，上線之後持續維護。維護時又會冒出新需求，再回到規劃，一圈一圈轉。

![SDLC 六個步驟排成一圈：規劃、設計、寫程式、測試、部署、維護，維護之後再回到規劃](/blog/ep088/sdlc.jpg)

這個系列沿著這一圈走。版本控制墊在整圈底下，每一步都用得到，所以第一集先講它。下一集，往測試跟部署走。

系列只講到你聽得懂 bot 在說什麼，知道哪一步輪到你拍板，指令交給 bot 去打。第一集先打大魔王：為什麼要版本控制，還有 Git 跟 GitHub。

打之前，先聊一件事：一般人跟工程師，用 AI 到底差在哪？

## 一般人跟工程師，用 AI 差在哪

先講我的看法：用同一個 AI，一般人跟工程師一開始做得出來的東西，差別其實不大。你跟它說想要一個預約頁，它一樣會寫給你，一樣跑得起來。

我甚至覺得，一般人跟 AI 互動的方式更跳脫框框。工程師腦袋裡有很多「這個應該很難」「這要排好幾個禮拜」。一般人沒有這些包袱，想到什麼就叫 AI 做，常常做出工程師不會去試的東西。

差距從第二版開始。第一版跑起來，你很開心，接著想加功能、改顏色、修一個 bug。改著改著，原本好好的地方壞了，你不知道是哪一次改壞的，也回不去。很多人的作品，就停在這裡。

拿開頭那個想做預約頁的老闆來說。預約頁第一版跑起來了，他叫 AI 加一個線上付款。AI 一口氣改了好幾個檔案，付款有了，可是預約日曆不見了。他說回到剛剛那版，AI 只能憑印象猜，猜錯又改壞一次。

工程師在這裡會自動做一些事：

- 改之前先存一個版本
- 把東西拆成幾塊
- 讓機器幫忙檢查有沒有改壞

這些是做久了的肌肉記憶，做的時候根本不會特別去想。差距就是這樣拉開的。

工程師是不是都這樣，我不知道，至少我是。我只要有一個概念走通了，就會很自然地想把它系統化，讓整個飛輪轉得更快。

我要的很簡單：輸出要維持穩定，最好越來越好；需要我動手介入的地方，越少越好。每找到一個要我盯著的變因，我就想辦法把它收進黑盒子裡，讓它自己處理。收得夠多，這一整套東西，就變成一個系統。

系統裡還有一個很重要的東西，叫回授。意思是結果會自己回頭，影響下一步。沒有回授的話，我不動，系統就不會發生任何改變，它只是一台等我按按鈕的機器。

小屋就是照這個想法長出來的：

1. bot 寫完程式，開一個 PR。
2. PR 一開，自動跑檢查、自動生一個測試網址。
3. 有事情發生，小屋把負責的那隻 bot 叫醒。
4. 結果再回到下一棒手上。

這些步驟，我都不用自己一個一個去按。

這個系列想補的，就是工程師那段肌肉記憶。你只要知道這些零件是什麼、什麼時候該叫 AI 用上它。第一個零件，也是最基本的一個，就是版本控制。

## 為什麼要版本控制

先講為什麼。你一定看過這種檔名：報告最終版、最終版二、真的最終版。改壞了想回去，找不到哪一份才是好的。

跟 AI 一起寫程式，這個問題會放大好幾倍。AI 一次可以改十幾個檔案，改得很快，也可能一口氣弄壞好幾個地方。你看不懂程式，就很難自己改回來。

你可能會想，按復原不就好了？編輯器的復原，只記得你在那個檔案裡打過的字。AI 一次改十幾個檔案，還會自己跑指令、搬檔案，復原鍵很難幫你全部救回來。

版本控制，就是幫你記下每一個版本：改了什麼、什麼時候改、為什麼改，隨時可以回到任何一版。Git 是現在最多人用的版本控制工具，[Stack Overflow 的開發者調查](https://survey.stackoverflow.co/2022/#section-version-control-version-control-systems)裡，九成以上的開發者都在用。

就算只有你一個人，加上 AI，其實就是兩個人在改同一份東西。AI 改了什麼，你需要一份紀錄。你自己改了什麼，AI 下次也要看得到。

學會它，你會得到三樣東西：

1. 敢讓 AI 放手改，改壞了退回去就好。
2. 聽得懂 AI 跟你回報什麼。
3. 抓別人的範本、裝工具、跟別人或別的 bot 一起做，背後都是它。

我先叫 bot 跑一次 teach，問它：小屋為什麼需要版本控制？回答大意是：

> 版本控制就像一本記帳簿，小屋已經記了一千一百多筆。修壁紙那個 bug，就是靠這本帳，把範圍縮到某一次改動之後，修好還順手加了一個自動檢查。沒有版本控制，後存的人會蓋掉前面的人，壞了也查不到是哪一次改壞的。

## 專案就是一個資料夾

要用 Git，先搞懂一件事：一個程式專案，就是電腦裡的一個資料夾。裡面放程式碼、圖片、設定，全部都是普通的檔案。小屋整個專案，就是一個叫 `pa-cafe` 的資料夾。

所以 Codex 叫你選專案，意思是：你要它在哪個資料夾裡工作。選好之後，它讀檔、改檔、跑指令，都在這個資料夾裡。Claude Code 也一樣，你在哪個資料夾打開它，它就在那裡做事。

開始的方法有兩種：

| 方法 | 怎麼做 |
| --- | --- |
| 從零開始 | 開一個空資料夾，取個名字，叫 Codex 打開它，跟它說你想做什麼 |
| 拿範本開始 | 把別人放在 GitHub 上的整個資料夾抓下來，這叫 clone，指令交給 AI 打就好 |

我看很多人卡住，是沒選資料夾就開始聊，做完找不到檔案。或是直接選了桌面、下載資料夾，裡面一堆不相干的東西。一個作品，開一個資料夾，就不容易亂。

選好資料夾之後，建議你偶爾打開來看一下。AI 做了哪些檔案、放在哪裡，看得到心裡就有底。跟它講話也能指名道姓，像是：改一下 `src` 裡面那個預約頁。

同樣問 bot：小屋這個專案資料夾裡有什麼？它把資料夾比成一間咖啡廳的圖紙：

| 資料夾 | 比喻 |
| --- | --- |
| `src` | 客人看得到的店面 |
| `worker` | 後場廚房 |
| `shared` | 前後場都照著做的規則本 |
| `tests` | 大約四百個檔案的自動檢查清單 |

這樣你想改店面還是後場，就知道該叫 AI 去哪個資料夾找。

## Git：幫資料夾存檔

資料夾有了，再來看 Git 怎麼存。打過電動就懂：打 Boss 之前先存檔，打輸了讀檔重來。每存一次叫一個 commit，上面記著這次改了什麼、誰改的、什麼時候改的。

### commit：存檔點與那句說明

每個存檔點都有一句說明，叫 commit message。小屋紀錄裡修壁紙那一筆，寫的是：一鍵布置後移動家具時，壁紙和地板不再變回預設。半年後回頭找，或叫 AI 查問題，靠的都是這一句。

什麼時候該存？比較好的習慣是：每完成一個能跑的小步驟，就存一次。加好一個按鈕，存。改好一頁，存。存得小，回頭的時候才不用一次丟掉一大堆。還有一點要記得：還沒存的改動，Git 也救不回來。

第一次存檔，AI 可能會問你的名字跟 email，因為每一筆紀錄都會寫上是誰存的。專案如果要公開，這兩個別人都看得到，可以請 AI 改用 GitHub 給你的隱藏 email。

### main：主線，與退回去

小屋的主線叫 main，到今天上面疊了一千一百多個存檔點。哪天 bot 改壞東西，翻回之前的存檔點就好。

回到以前的版本還有一個好處：後來的紀錄不會被丟掉。你退回昨天那版，今天改過的東西還留在紀錄裡，哪天想拿回來，一樣找得到。

### branch：每隻 bot 一條線

可是好幾隻 bot 同時改同一份程式，不就打架了？所以有分支，英文叫 branch。每隻 bot 從主線分出一條自己的線，在上面慢慢改、慢慢存，主線照常運作。

![主線 main 分出 bot A、bot B、bot C 三條分支，各自在自己的線上存檔，main 照常運作](/blog/ep088/branch.jpg)

像前幾天修的一個 bug：一鍵布置之後去移動家具，壁紙跟地板會變回預設。修它的分支，名字直接寫要修什麼：

```text
fix/arrange-keeps-finishes
```

這條分支改了兩個檔案，存了一次。

### worktree：一隻 bot 一個資料夾

分支還有一個限制：一個資料夾，同一時間只能站在一條分支上。好幾隻 bot 要同時改，擠在同一個資料夾裡，就會互相踩到。

這時候用 worktree：同一個專案，多開幾個資料夾，每個資料夾站在自己的分支上，存檔紀錄還是同一份。我讓好幾隻 bot 同時做事，就是每隻各開一個 worktree。

![左邊：一個 booking 資料夾一次只站一條分支，bot A、B、C 會互相踩到。右邊：booking、booking-pay、booking-fix 三個 worktree 資料夾各站一條分支，共用同一份 .git 紀錄](/blog/ep088/worktree.jpg)

### merge、衝突與 diff

分支改好了，要併回主線，這個動作叫 merge，合併。如果兩條分支剛好改到同一個地方，Git 會停下來問你要留哪一個，這叫衝突。聽起來可怕，現在叫 AI 幫你解就好，你只要決定要哪個結果。

還有一個很好用的東西叫 diff，就是兩個版本之間差了什麼：加的是綠色，刪的是紅色。拿預約頁的例子來看，大概是這樣：

```text
booking.html    +12 −3
calendar.js     +4 −18

+ 線上付款按鈕
− 預約日曆
```

AI 改完，你看不懂程式也沒關係，看 diff 至少知道它動了哪幾個檔案、改了多大。

### .gitignore：不該存的東西

有些東西不該存進去，像密碼、API 金鑰。專案裡有一個叫 `.gitignore` 的檔案，寫在裡面的東西，Git 就不會記。小屋的 `.gitignore` 節錄如下，放金鑰的 `.env` 檔就被排除在外：

```text
node_modules/
dist/
.env*
!.env.example
.dev.vars*
```

這點很重要。存進去再推上 GitHub，別人就可能看得到。

### 存檔藏在哪

這些存檔點放在專案資料夾裡一個叫 `.git` 的隱藏資料夾。所以 Git 本身不用網路。你 clone 別人的專案，抓下來的就是整個資料夾，加上這份存檔紀錄。

我叫 bot 實際跑一次 teach，問它：小屋怎麼用 commit 跟 branch？回答大意是：

> 改動先存在自己的分支，還附了一個新的測試檔，審過才併回 main。併進 main 只會更新測試站，正式站跟的是另一條線。

### 喚醒 AI 的咒語

現在的 coding agent，Git 怎麼操作它都很清楚，只是很多時候你沒開口，它就不會主動做。你需要的，是幾句把它喚醒的咒語。

第一句最重要：新的專案資料夾，先叫它 `git init`，意思是在這個資料夾開始用 Git 記錄。

```text
幫我 git init
```

其他咒語也很短：

| 時機 | 對 AI 說 |
| --- | --- |
| 做完一步 | 幫我 commit 起來 |
| 要試新功能 | 開一個新分支來試 |
| 改壞了 | 回到昨天那個能跑的版本 |

指令不用背，剩下的它會幫你打。

## GitHub：生態系的中心

Git 是你電腦裡的存檔工具。GitHub 是一個網站，讓大家把專案資料夾連同存檔推上去放。推上去叫 push，把別人的新存檔抓下來叫 pull。

![你的電腦（Git：存檔工具）與 GitHub（大家共用的存檔站）之間，push 把存檔推上去，pull 把新存檔抓下來](/blog/ep088/push-pull.jpg)

GitHub 是整個生態系最重要的一站：

- 別人寫好的範本跟工具，大多放在上面。
- 你裝的 AI 技能，像 pstack，也是從 GitHub 抓下來的。
- 問題回報、討論、說明文件，也都在那裡。
- 你自己的專案推上去，電腦壞了也還在。

### 免費開始

GitHub 要錢嗎？[開帳號免費](https://github.com/pricing)，私人專案也能免費開，只有你自己看得到。所以第一步很簡單：開一個 GitHub 帳號，請 AI 幫你把專案推上去。

設成公開的專案，任何人都看得到，也都能 clone 下來。很多好用的範本就是這樣分享出來的。你自己的專案要公開之前，先確認裡面沒有密碼。

GitHub 上每個專案的首頁，都會顯示一份叫 README 的說明，寫這個專案是什麼、怎麼用。叫 AI 抓範本之前，先看一下 README，就知道它適不適合你。

### 登入授權與推不上去

讓 AI 幫你推上 GitHub，第一次會要你登入、授權。這一步請你自己來，帳號密碼不要貼給 AI。

推上去偶爾會被擋下來，常見的原因是 GitHub 上已經有比你新的存檔，像是你在另一台電腦改過。這時候叫 AI 先 pull 下來，再推一次就好。

### PR：請把我這條線合進 main

分支改好了，要怎麼併回主線？在 GitHub 開一個 PR，全名 pull request，意思是：我這條線改好了，請把它合進 main。PR 頁面會列出改了哪幾行，大家在上面留言、審查，沒問題就按合併。

修壁紙那個，就是小屋第 874 號 PR。小屋每一個改動都走這條路：先開分支，再開 PR，合併之後才進主線。十月中有一個禮拜，就合併了 276 個。

![GitHub Pulse 頁面，2026 年 10 月 15 日到 22 日：276 個 merged pull requests、6 個 open pull requests、5 個 closed issues、5 個 new issues](/blog/ep088/pulse.jpg)

PR 還是一個討論的地方。你可以在上面留言說這裡不對，bot 照著留言再改一版，改到你滿意才合併。這也是一種回授。

### issue：先記下來

GitHub 上還有一個地方叫 issue，就是問題回報跟待辦清單。發現 bug，不用馬上修，先開一張 issue 記下來，之後再叫 bot 一張一張處理。小屋十月中那個禮拜，就新開了 5 張、關掉了 5 張。

同一招拿來問 PR。teach 自己挑了前幾天修萬聖節家具的那一張，回答大意是：

> 先從 main 開一條分支，改了三個檔案，再開 PR 申請合併。機器先跑一排檢查，檢查都過、有人看過，才按合併。

## 跟著老闆走一遍

把今天講的，跟著那位老闆走一遍。

他在桌面開了一個叫 `booking` 的資料夾，叫 AI 打開它，第一句先說：幫我 git init。接著說：幫我做一個預約頁。第一版跑起來之後，他多講了一句：幫我 commit 起來。

接著想加線上付款。這次他先說：開一個新分支來試付款。AI 在分支上改，主線那個能跑的預約頁，原封不動。

付款做好了，日曆又不見了。這次他不用慌，叫 AI 看一下 diff，發現是改到了日曆那個檔案。修不好也沒關係，切回主線，昨天那版還在。

付款終於弄好，他開了一個 GitHub 帳號，自己登入授權，叫 AI 把專案推上去、開一個 PR。看過改了哪些地方，按下合併。電腦就算明天壞掉，預約頁也還在。

他自己試的時候，發現週末的時段顯示錯了，先開一張 issue 記下來，晚上再叫 bot 去處理。

到這裡，他已經在用工程師那套肌肉記憶，只是指令都交給 AI 打。他今天講過的話整理如下：

| 他說的話 | 發生什麼事 |
| --- | --- |
| 打開資料夾 | AI 在 `booking` 資料夾裡工作 |
| git init | 資料夾開始用 Git 記錄 |
| commit 起來 | 第一版預約頁存成一個存檔點 |
| 開分支 | 線上付款在分支上做，main 不動 |
| 看 diff | 發現日曆那個檔案被改掉 |
| 切回主線 | 昨天那版預約頁回來了 |
| 推上去開 PR | 專案進 GitHub，看過改動後合併 |
| 開 issue | 週末時段的問題先記下來 |

八句話，他一行指令都沒打。

## 版本控制是飛輪的第一個零件

回到前面講的系統化。版本控制，是整個飛輪的第一個零件。有了存檔點，才敢讓 AI 放手改。有了分支跟 PR，才能讓好幾隻 bot 同時做事，又不會打架。

它也是回授的起點。每一次改了什麼、為什麼改，都記在紀錄裡。PR 上的留言、檢查結果，都會回到 bot 手上，讓它知道下一步怎麼修。紀錄留得越完整，系統越能自己往前走。

小屋現在的樣子，就是一層一層疊起來的：

| 層 | 內容 |
| --- | --- |
| 最底下 | Git 存檔 |
| 往上 | bot 的分支和 PR |
| 再往上 | 自動檢查跟測試站 |
| 最上面 | 用事件把 bot 叫醒 |

每多一層，我要盯的就少一點。你先疊好 Git 這一層就夠了。你的作品會從改壞了回不去，變成隨時有退路。

還有一件事。程式推上 GitHub、合併進 main，客人打開網址，看到的還是舊的。GitHub 上放的是程式碼。要讓客人看到新版，還差一步，叫部署，把程式放到一台一直開著的主機上跑。小屋合併進 main 之後，會先自動更新測試站，打了發版標籤，正式站才會更新。

再往上疊，就是部署這一層：PR 開好之後自動跑的檢查，還有測試站、正式站這些環境。這些零件一個一個收進黑盒子，你要介入的地方就越來越少。那是下一集要講的。

## 打完大魔王

回到開頭那個問題：一般人跟工程師，用 AI 差在哪？差在做完第一版之後，有沒有一套讓作品越改越好、又不用一直盯著的方法。版本控制，就是這套方法的第一步。

開資料夾、存 commit、推上 GitHub、開 PR，大魔王就這樣打完了。

### 名詞速查

| 詞 | 白話 |
| --- | --- |
| commit | 一個存檔點，記著改了什麼、誰改的、什麼時候改的 |
| commit message | 每個存檔點的那一句說明 |
| main | 主線 |
| branch | 從主線分出來的一條線，讓每隻 bot 各改各的 |
| worktree | 同一個專案多開幾個資料夾，每個站在自己的分支上 |
| merge | 把分支併回主線 |
| 衝突 | 兩條分支改到同一個地方，Git 停下來問你要留哪一個 |
| diff | 兩個版本之間差了什麼 |
| `.gitignore` | 寫在裡面的東西，Git 不會記 |
| clone | 把整個專案資料夾連同存檔紀錄抓下來 |
| push / pull | 推上 GitHub / 把新存檔抓下來 |
| PR | 請把我這條線合進 main，大家可以在上面留言審查 |
| issue | 問題回報跟待辦清單 |
| README | 專案首頁的說明，寫這個專案是什麼、怎麼用 |

### 這週的作業

如果你想動手試，這週做三件事：

1. 開一個新資料夾，叫 AI 先 `git init`，再在裡面做一個小東西。
2. 請它 commit 起來。
3. 開一個 GitHub 帳號，把它推成私人專案。

遇到聽不懂的詞，就用 teach 問它。

想看看這些 PR 最後變成什麼樣子，可以去 [PA Cafe](https://pacafe.dnplus.dev) 開一間自己的小屋。免費就能開始，先讓兩隻 bot 住進來。
