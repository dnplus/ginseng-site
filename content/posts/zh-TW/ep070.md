我本來只想把 Codex 週額度最後那 2% 用完，結果一次 Codex Security 掃描，半天跑掉將近 **60 億 Token**。週額度見底之後，它沒問我，直接扣了一萬兩千點；最後掃描狀態還是 **FAILED**。這篇我用本機的 Codex session 紀錄把整件事拆開：60 億怎麼在半天內噴出來、花在哪些 agent 身上、點數從什麼時候開始扣，還有那份報告最後是誰補完的。

> 🎬 影片：[Codex 半天用掉 6B Token，怎麼辦到的？！](https://youtu.be/GEPMAzq7mEo)

## 起點：反正要重置，不用白不用

事情從 Tibo 的一則貼文開始。Tibo 是 OpenAI 負責 Codex 的人，台灣時間 10 月 2 日上午，他在 X 上說隔天「10am PST」要幫所有付費帳號重置用量。換成台灣時間，大概是 10 月 3 日凌晨一點到兩點，我就抓凌晨一點。

額度留著也是歸零，不用白不用嘛。

[Tibo（@thsottiaux）在 X 的重置公告](https://x.com/thsottiaux/status/2105843926221660585)

[SmartScope：Tibo 公告的 Codex 重置時間整理](https://smartscope.blog/en/blog/codex-usage-reset-time-announced-tibo-all-paid-2026/)

剛好前一天我才通過 **Daybreak Blue**。這是 OpenAI 資安存取計畫裡的防禦層級，給找漏洞、做安全審查這類防守工作用。既然拿到了，就來跑一次完整的 Codex Security 掃描：讓 Codex 把整個專案讀過一遍，列出可能的漏洞，再驗證、去重，整理成一份報告。

[The Decoder：OpenAI DevDay 的 Codex Security 與 Daybreak Blue](https://the-decoder.com/openai-expands-codex-and-its-api-at-devday-with-security-scans-a-decisions-api-and-ultrafast/)

我腦中的劇本很簡單：把剩下的額度用完，拿到一份報告，過了重置時間，明天又是一條好漢。結果隔天下午，我看到當天的用量：**61.23 億 Token**。我先把小數點看一遍，再把單位看一遍。對，是億。

## 重置晚了四個小時，掃描沒停

那天下午，我的週額度只剩 18%。欸？我原本是在清冰箱，怎麼連下禮拜的菜都一起煮了？

後來我把本機的 session 紀錄對出來，時間線是這樣（台灣時間）：

- 10/02 22:25：掃描開始
- 10/03 00:55：週額度見底
- 01:00–05:13：掃描沒停，開始扣點數
- 05:13：重置真的生效
- 13:07：最後一個 agent 停下

Tibo 說的重置，我的帳號是凌晨 **5 點 13 分**才生效，比我以為的晚了四個多小時。週額度在凌晨一點前就用完，中間這四個小時，掃描燒的是點數。重置之後它也照跑，新一週的額度一路吃到八成多，所以下午只剩 18%。

很會省的人，通常就是我這種人。

## 它沒問，直接扣點

被燒掉的點數，是 DevDay 那波送的。9 月 29 日 DevDay 調整了 Pro 方案，200 美元的 Pro 從 Plus 的 20 倍用量降到 10 倍，Pro 用戶拿到 **62,500 點**補償，12 月 31 日到期。

[The Decoder：DevDay 上的 Pro 方案調整](https://the-decoder.com/openai-expands-codex-and-its-api-at-devday-with-security-scans-a-decisions-api-and-ultrafast/)

[LATENT：62,500 Codex 點數的通知與用法](https://latent.tokyo/en/articles/2026-09-30-codex-62500-credits)

我本來以為，額度用完它會先問我：要用 reset，還是用點數繼續跑？我記得以前是這樣。這次它沒問，直接扣下去。紀錄上 00:55 週額度到 100%，01:00 點數就開始往下掉，掃描完全沒有停頓：四個小時從 **61,346 點掉到 49,303 點**，大約 **12,043 點**，62,500 點一個晚上就去了快五分之一。

打開點數頁面，七天已使用 13,210 點，最大根的柱子就在 10 月 3 日，幾乎整根都是 Codex 的藍色。我原本只會很籠統地說「我噴了一萬多點」，現在系統還幫我的心痛加上了千分位。

照 OpenAI 的說明，這就是設計好的順序：**先用方案內含的額度，用完就從點數扣。** 帳上有點數，任務就會繼續跑。已經有人在 Codex 的 GitHub 開 issue，希望有「額度用完先停」的選項，或至少跳一個確認視窗。

[OpenAI 說明：Using Credits for Flexible Usage in ChatGPT (Personal plans)](https://help.openai.com/en/articles/12642688-using-credits-for-flexible-usage-in-chatgpt-personal-plans)

[openai/codex Issue #48394：Codex credits - usage limit](https://github.com/openai/codex/issues/48394)

點數是送的，不是我刷了一萬多塊。可是免費的東西一進帳戶，我就開始覺得它本來可以留著做很多事。它還在的時候叫贈品，它消失的時候，我突然對每一點都有感情。

## 一個半小時，怎麼噴出 60 億

最近大家才在抱怨 Codex 跑很慢，結果我畫面上寫著：**1:32:04**。一個半小時，六十幾億 Token？

對完紀錄才知道，那 1 小時 32 分只是其中一個回合。那個回合回我說掃描還沒做完，之後那個 session 就再也沒回話。可是背景的 agent 沒停：前一天晚上 10 點多開始，中間停了一段（23:22–01:08），然後一路跑到隔天下午 1 點。

而且不是一個 agent 在跑。掃描期間每個完整的小時，都同時有 **17 到 18 個 agent** 在開工，每小時吃掉 5 億左右的 Token。10 月 3 日從 01:08 跑到 13:07，大約 12 個小時，加起來就是 59 億多。單一個 agent 不快，十八個一起跑上半天，就是 60 億。

**不是 Codex 突然變快，是它一次開了一整間辦公室。**

## 190 個 session，60 億花在哪

10 月 3 日全部用量是 61.23 億，直接跟這次掃描有關的大約 59 億，占九成六以上。看起來只是一次掃描，背後是 **190 個 session**：38 組 discovery 工作，每組一個主 agent，底下再掛 3 個子代理（baseline、專門追某一類問題、architecture），另外還有 38 輪負責去重、彙整結果。

照角色分開算：

| 角色 | session 數 | Token | 占比 |
| --- | --- | --- | --- |
| discovery 主 agent | 38 | 18.41 億 | 31.1% |
| 子代理：baseline | 38 | 14.53 億 | 24.5% |
| 子代理：專門追某一類問題 | 38 | 13.34 億 | 22.5% |
| 子代理：architecture | 38 | 12.23 億 | 20.6% |
| 去重、彙整 | 38 | 0.76 億 | 1.3% |

子代理加起來吃掉 **67.6%**，負責收尾的去重只用了七千多萬，不到 2%。**Token 幾乎都花在到處找，收尾反而很省。**

這 59 億裡，大約 95% 是 cached input，也就是重複送進模型、吃得到快取的輸入。OpenAI 的 prompt caching 說明寫得很清楚，快取的輸入用比較低的價格計算。便宜，但不是免費；量堆到 60 億，便宜的東西也會變貴。

[OpenAI — Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

## 3,035 個檔案、188 筆候選，最後是 FAILED

它是真的有在做事。這次範圍有 3,035 個檔案，中途整理出 188 筆候選問題。看到這些我還有點期待：這麼認真，報告應該很精彩吧？

不過候選還要驗證、去重，不能每一條都算成確定的漏洞。就像健康檢查做了一堆項目，看到幾個星號，也還不等於每一個都確診。我等的是最後那份整理好的報告：哪些真的有問題、證據是什麼、怎麼判斷的。總不能拿著一百多條候選清單，先幫自己開記者會。

結果 Deep Scan 的最終狀態是 **FAILED**。

原因就是前面那件事：那個回合說還沒好，之後 session 就不再回話。背景的 agent 一個個跑完了，最後的報告卻沒有生出來。前面那麼多工作，沒有一份能直接打開的結果。

所以最後是我自己動手：把它已經產生的證據撈出來，再叫 Codex 重新分類、去重，把報告重建出來。**花了 60 億 Token 的掃描，最後一哩路是我手動補完的。**

## 想趁重置前把額度用完，先看這三件事

- **重置看實際生效的時間**：公告寫隔天 10am PST，我的帳號是台灣時間 05:13 才重置。中間差的那四個小時，長任務不會停下來等你。
- **週額度見底，點數會直接接上**：帳上有點數，任務就繼續跑。不想動到點數，就要自己盯著用量。
- **看同時開了幾個 agent，不要只看單一回合**：畫面上一個回合 1 小時 32 分，背後是十七、十八個 agent 並行跑了十幾個小時。燒多快，看的是這個。

## 最後那 2%，有沒有浪費

回頭看，起點真的非常樸實：我只是看到 2%，覺得不用掉很可惜。然後事情一路長成 60 億 Token、18 個 agent 同時開工、一萬兩千點的 DevDay 點數，最後是一個 FAILED，跟一份我自己重建的報告。

「反正要重置，不用白不用」這句話，我覺得可以印出來，放在滑鼠旁邊。它帶走了一萬兩千點，還有新一週的八成。這支影片的素材，倒是沒有浪費。

說到底，agent 現在真的很方便，一句話就能叫一整間辦公室幫你開工。可是**額度是你的，點數是你的，最後那一哩路也還是你自己補**。等哪天它能自己繳帳單，可能就不一樣了吧。

你有沒有也為了不浪費額度，結果用得更多？到影片底下留言跟我說。
