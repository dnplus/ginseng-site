你用 Grok Bot、dots 這類 AI 助理，可能遇過這種時刻：信一進來，它就主動跑來跟你說，順便把事情處理掉。這篇從零講輪詢跟事件驅動：它們怎麼運作、為什麼直接決定你的 token 燒多快，各家怎麼做「門鈴」，還有我做的 PA Cafe 小屋，怎麼把通知跟 bot 分開。

## 輪詢：每隔一段時間去看一次

最直覺的做法是排程：每隔五分鐘，叫 bot 去看一下有沒有新信。這招叫輪詢，英文 polling。以前在電腦上跑排程，花的是 CPU；換成 AI 助理，它每醒來一次都要讀指示、呼叫工具、把結果撈回來看，每一步都在花 token。

每五分鐘一次，一天就是 288 次。假設一天只來三封重要的信，剩下 285 次，都是醒來看一眼空信箱。

![每 5 分鐘看一次：一天 288 次，大部分是空轉](/blog/ep087/zh-TW-01.webp)
*每 5 分鐘看一次：一天 288 次，大部分是空轉*

我實際量了一次。用 Codex 跑一輪最簡單的檢查：讀一個本機的信箱檔，看有沒有新信。它回我四個字「沒有新信」，這一輪的輸入是 58,023 個 token，其中 28,800 個是快取讀取。我看大部分是它每次醒來都要整包重讀的指示和工具說明。照這一輪推算，乘上 288 次，一天大約 1,670 萬個 token，大部分花在「沒有新信」。（2026-10-31 用 Codex CLI 實測）

![Codex 跑一輪空檢查：輸入 58,023 個 token，回答四個字](/blog/ep087/zh-TW-02.webp)
*Codex 跑一輪空檢查：輸入 58,023 個 token，回答四個字*

那排鬆一點，一小時看一次？省是省了，信進來之後最久要等快一個小時它才知道。排密燒 token，排鬆消息慢，輪詢就卡在這兩邊。

## 事件驅動：有事才按門鈴

事件驅動把方向倒過來：bot 平常睡覺，信箱那邊一有新信，就主動按門鈴把它叫醒。這個門鈴，技術上通常就是 webhook：你給對方一個網址，對方有事的時候往這個網址打一筆通知，裡面帶著發生了什麼。

![門鈴就是 webhook：登記網址，有事就送一筆通知過來](/blog/ep087/zh-TW-03.webp)
*門鈴就是 webhook：登記網址，有事就送一筆通知過來*

這個觀念很老。1950 年代初期，電腦就有[中斷（interrupt）](https://en.wikipedia.org/wiki/Interrupt)。到現在你按鍵盤也是這樣：鍵盤主動送訊號給 CPU，CPU 不用一直繞圈去問。手機的推播也是同一套。

輪詢跟門鈴中間，還有[長輪詢](https://www.rfc-editor.org/rfc/rfc6202)、[WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)、[SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。這幾種都要接收的那一端一直開著連線，所以實務上，是讓一般程式或平台先接住通知，再用門鈴叫醒 bot。

排程還是有它的位置。每週一整理上週數字、每天早上看行程，這種固定時間的事交給排程；不知道什麼時候會來的事，交給事件。

## 各家都在做門鈴

- Claude Code 的雲端排程任務（以前叫 routines），除了排時間，也能用 API 或 GitHub 事件觸發。[官方文件](https://code.claude.com/docs/en/routines)
- OpenAI 在推 MCP Events：外部服務有新訊息、狀態改了，就打一筆簽過名的通知給 ChatGPT，dots 也支援。[官方文件](https://developers.openai.com/plugins/build/mcp-events)
- Grok Bot 的 routine 有 webhook 觸發，每條 routine 一個專屬網址。[官方文件](https://docs.x.ai/grok-bot/skills-routines-and-automations)

## Bot 為什麼看起來很主動

Grok Bot 用 connector 接上 Gmail 之後，能幫你搜信、讀信、寄信（[官方文件](https://docs.x.ai/grok-bot/computer-and-apps)）。可是光接上去，新信到了它不會自己醒；要它有事就醒，得再建一條 routine。routine 可以設成 GitHub、Sentry 有動靜、信寄到它自己的信箱，或是有人打它的 webhook，就把它叫起來做事（[官方文件](https://docs.x.ai/grok-bot/skills-routines-and-automations)）。routine 被觸發，bot 醒過來，讀內容、整理、跟你回報。你只看到最後回報那一步，所以覺得它很主動。

![後台一串事件在接力，你只看到最後的回報](/blog/ep087/zh-TW-04.webp)
*後台一串事件在接力，你只看到最後的回報*

信要能叫醒它，Grok Bot 多給一條路：跟它說一聲，就能領一個它自己的信箱。再建一條 routine，信寄到這個信箱就會叫醒它（[官方文件](https://docs.x.ai/grok-bot/computer-and-apps#give-your-bots-an-email-address)）。像它幫你申請帳號、收驗證信，驗證信通常有期限，過了十幾分鐘才去查可能就失效了，這種要接力的事交給事件最穩。

## 門鈴裝在誰家

每一家的門鈴規格都不一樣：dots 走 MCP Events，Grok Bot 走 routine webhook，Claude Code 又有自己的 API。我自己是輪流用的，額度用完就換下一隻，每換一次，Notion、Gmail 這些通知就要重接。通知綁死在某一家 bot 身上，這就是 vendor lock-in，供應商鎖定。

## 小屋：通知跟 bot 分開

這是我做 [PA Cafe](https://pacafe.dnplus.dev) 這間小屋的原因。小屋是讓好幾隻 bot 住在一起、共用通知的地方：通知先進小屋，小屋再叫醒該接的那一隻。

![事件來源跟 bot 本身分開](/blog/ep087/zh-TW-05.webp)
*事件來源跟 bot 本身分開*

背後的原理很簡單：不需要動腦的事，先讓電腦做掉。收通知、記下來、挑出該叫醒的那一隻，都是一般程式在跑，燒的是 CPU；真的要讀、要判斷、要寫的時候，才叫醒 bot。

![先燒 CPU，再燒 token](/blog/ep087/zh-TW-06.webp)
*先燒 CPU，再燒 token*

我看這些 AI 公司的內建機制，也是同一個思路，公開價格裡就看得到：Anthropic 跟 OpenAI 的批次 API 打五折（[Anthropic](https://platform.claude.com/docs/en/docs/build-with-claude/batch-processing)、[OpenAI](https://developers.openai.com/api/docs/guides/batch)），Anthropic 的[快取讀取](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching)最多只收原價一成。

## 接力：從寫程式到上線

我現在的組合是讓 Grok Bot 去指揮 Codex 或 Claude Code 寫程式，這些 coding agent 都開在 Herdr 裡。Herdr 可以想成新一代的 tmux，專門為 coding agent 優化：它認得每個窗格裡的 agent 在跑、卡住還是做完了。

終端機視窗關掉、SSH 斷線，裡面的 agent 照樣在背景跑。電腦關機重開，工作區、分頁和每個窗格的資料夾會原樣排回來；有接 Herdr 整合的 agent，還會用各自的 resume 指令接回原本那段對話，正在跑的指令則會停掉。（[Herdr 文件：Session state and restore](https://raw.githubusercontent.com/herdrdev/herdr/v0.9.5/docs/next/website/src/content/docs/session-state.mdx)）

![Herdr 關機重開，工作原樣回來](/blog/ep087/zh-TW-07.webp)
*Herdr 關機重開，工作原樣回來*

Herdr 做完或卡住會叮一聲，可是這個叮叮叮是叮你的，bot 聽不到。我最常遇到的卡法是審批：agent 跳出來問你准不准，就停在那裡，bot 不知道。裝上 [agent-webhook-notify](https://github.com/happyeric77/agent-webhook-notify) 這類外掛，agent 一做完、一卡住就打一筆 webhook 出去。我把它接到小屋，小屋叫醒負責的 bot，卡在審批它馬上回報、問你要不要放行；做完了就接下一步。

![外掛把叮叮叮接給 bot](/blog/ep087/zh-TW-08.webp)
*外掛把叮叮叮接給 bot*

在小屋裡，這一段長這樣：外部來源接了 Herdr，最近事件寫著「Codex 卡住：等你審批」；Grok Bot 接手之後，傳到你的手機問要不要放行。下面兩張是小屋的真實介面，資料是示範用的。

![小屋的外部來源：Herdr 的最近事件](/blog/ep087/zh-TW-09.webp)
*小屋的外部來源：Herdr 的最近事件*

![Grok Bot 傳到手機：Codex 卡在審批，要放行嗎？](/blog/ep087/zh-TW-10.webp)
*Grok Bot 傳到手機：Codex 卡在審批，要放行嗎？*

後面接著 GitHub：PR 一開就發事件，叫醒負責 QA 的 bot 去審查；審完合併、部署狀態更新也都會發通知（[GitHub 文件](https://docs.github.com/en/webhooks/webhook-events-and-payloads)）。上線之後，Sentry 這類錯誤監控的告警規則一觸發，就能打 [webhook](https://docs.sentry.io/organization/integrations/integration-platform/webhooks/issue-alerts/) 出來，叫醒監控 bot 去判斷是不是這次上線帶進來的錯，要不要退版。這幾隻 bot 也可以來自不同家，大家住在同一間小屋，事件進小屋再派給對的那一隻。

![每一棒都被上一棒的事件叫醒](/blog/ep087/zh-TW-11.webp)

## 門鈴的備案與保養

- 沒有門鈴的服務：寫一支一般程式去輪，跟上次比對，內容有變才叫醒 bot。可以放在自己電腦的排程，或 [GitHub Actions 的 schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。
- 驗簽：多數 webhook 會簽名，或帶一把金鑰。GitHub 用 [X-Hub-Signature-256](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)，MCP Events 用 [Standard Webhooks](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md)。我接小屋用的 Herdr 通知外掛，送出去的通知也照 Standard Webhooks 簽名。

![收到通知先驗簽，對不上就丟掉](/blog/ep087/zh-TW-12.webp)
*收到通知先驗簽，對不上就丟掉*

- 重送：照 Standard Webhooks 的規格，送不到會重送，每次帶同一個編號，收的一方記住處理過的編號，同一件事就只做一次。GitHub 送失敗的通知[不會自動重送](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries)，要自己補送。
- 我看比較穩的做法是混著用：平常靠事件，再留一條很稀的排程當備援，比如一天對帳一次，把漏掉的撿回來。

## 翻排程時問三件事

1. 這條排程在等什麼？
2. 等的那件事，有沒有門鈴？
3. 沒有門鈴的話，能不能先讓一般程式去輪，有變化才叫醒 bot？
