## AI 說做好了

先講一個你可能遇過的情境。你叫 AI 幫預約網站加一個優惠券功能，它跑完，回你一句：做好了，測試全過。你很開心，推上線。隔天有客人傳訊息來：怎麼付不了款？優惠券好好的，壞掉的是付款按鈕。你回去叫 AI 修，它說抱歉，馬上修好。修完，換會員登入壞掉。最後幫你測試的，是你的用戶。

有一位工程師，網路上叫 poteto，她寫過，自己一個月可以把兩千個 PR 送上正式環境，而且有把握它們是好的。她說，敢這樣放手，最關鍵的是驗證。這篇從測試講起，再講到驗證。

內容分三段：先講測試是什麼、為什麼上線之後更需要它；再講 poteto 的驗證優先，拿小屋走一遍；最後寫我自己的看法，也就是為什麼我不走規格先行這條路。

這是「小屋技術白話課」的第五篇。上一篇講 CI，我寫過 CI 能檢查多少，看你有多少測試，這篇接著講測試。一樣不必買課，每講一個詞，我就叫 bot 用 pstack 的 teach 拿小屋跑一次，你也可以拿自己的專案問一次。

## 測試是什麼？用咖啡店講

繼續開那家咖啡店。上一篇說 CI 是出餐前的品管台，每改一次配方，就自動試做一杯。試做完，品管台怎麼知道這杯對不對？它手上要有一張試喝標準卡：拿鐵幾 cc、幾度、奶泡多厚。

測試就是那張標準卡，只是寫成程式。它寫的是：輸入這個，應該得到那個。對了亮綠燈，錯了亮紅燈。CI 每次跑的，就是把整疊標準卡拿出來，一張一張對過去。

標準卡有三種粗細。

- **單元測試**最細，只檢查一個步驟，像糖漿是不是 15 cc。換成預約網站，就是檢查算價錢的那段程式：原價一千、打八折，算出來是不是八百。這種跑得很快，幾秒就能對完幾百張。
- **整合測試**在中間，檢查兩個步驟接起來對不對：點單機把單送到吧台，吧台收到的是不是同一杯。換成程式，就是預約頁把資料送進資料庫，存進去的時段有沒有跑掉。
- **端到端測試**最粗，英文 end to end，常縮寫成 e2e。它從客人推門開始：點單、付錢、拿到咖啡，整條走一遍。換成預約網站，就是開一個真的瀏覽器，像用戶一樣點：選時段、登入、付款，最後看到預約成功。

越細的跑越快，壞了也越好找是哪裡；越粗的越慢，卻最接近客人真的會遇到的事。所以一般的做法，是細的寫很多，粗的挑幾條最重要的路線就好。

我叫 bot 用 teach 問了一題：小屋有快五百個測試檔，又有一份驗證 skill，這兩個各自在顧什麼？它的回答是，測試顧的是程式有沒有照約定運作，像每則更新紀錄是否都有五種語言；驗證 skill 顧的是人真的用不用得了，它會在本機開一個真的瀏覽器，像用戶一樣建立咖啡館、改店名、重新整理，確認店名還在。

它還講了一句我很同意的：AI 常常把程式跟測試一起寫，兩邊可能錯在同一個地方。照開頭那個情境，AI 測了優惠券，沒測付款，所以它說測試全過，付款照樣壞掉。

## 上線只是第一天

為什麼用 AI 寫程式的人更需要測試？第一個原因，AI 最常講的一句話，就是做好了。它可能真的做好了，也可能只是程式能編譯、跑得起來。能編譯，只能證明打字沒打錯；功能對不對，要有東西真的去對過才知道。

第二個原因更重要：服務上線，只是第一天。之後你會一直改，加功能、改介面、升級套件、修 bug。每改一次，都有機會把舊功能弄壞，而且壞掉的地方，常常離你改的地方很遠。

沒有測試的話，你只能每次改完，把所有功能自己點一遍。功能少還點得完；到了十個、二十個功能，你就會開始只點剛改的那個，舊的留給用戶幫你發現。

小屋就遇過一次。11 月 3 號，bot 把咖啡豆從商店裡的一個分頁，搬成自己獨立的面板。新面板很好看，一個舊行為卻被搬丟了：讀資料失敗的時候，舊分頁會顯示錯誤，旁邊還有一顆再試一次的按鈕；新面板只會一直顯示載入中，永遠停在那裡。

這是上線前的檢查抓到的。修它的那個 PR 分兩步：第一步只加一個測試，寫明讀資料失敗時，要出現錯誤跟再試一次。這個測試一跑就紅燈，證明它真的抓得到這個坑；第二步才修程式，紅燈變綠燈。同一天就合併了。

從那天起，只要有人再改到咖啡豆面板，CI 都會再驗一次這件事。每補一個測試，就是幫一個功能買保險。小屋現在有五千多個測試，改到產品程式的 PR，CI 都會把它們全部跑一遍。

## poteto 憑什麼敢放手？

poteto 本名 Lauren，待過 Meta、Netflix，也在做 AI 寫程式工具的 Cursor 做過，還是 React Compiler 的核心成員。她把自己每天用的做法開源成一套技能包，就是這個系列一直在用的 pstack。

一個月兩千個 PR，要怎麼放心？她把 agent 比喻成很有才華、卻很健忘的新人。新人做完事，你放心不下，就只能每一件都自己檢查一遍；agent 也一樣，它沒辦法自己驗證，每個結果都會回到你手上，等你一個一個手動檢查。

pstack 的指南講得很白：大部分 agent 的工作裡，最慢的一步就是驗證，因為這一步通常在等人。讓 agent 自己會驗，你就脫離了卡關的位置；跳過這一步，開再多隻 agent，也只是多出一堆沒人檢查的東西，等著你看。

所以她說，工具箱裡最關鍵的，是一個好的驗證 skill，讓 agent 自己把 app 開起來、自己去點、自己看結果。她在指南裡也寫，整份指南裡，這一步回報最大。

她的做法有三條規矩。

**第一條，能編譯不算證據。** pstack 的說明文件寫得很直接，agent 回報做完，要附上真的跑過的結果，像指令跟輸出、截圖、影片。拿不出證據、口氣又很有把握的回報，反而要提高警覺。

**第二條，寫程式的 agent 不能自己判定過關。** pstack 要上線之前，會另外派一隻沒寫過這段程式的 agent，把功能實際跑一遍。前面 teach 講的就是這件事：程式跟測試一起寫，錯的話兩邊一起錯，換一個人來驗，才抓得到。

**第三條，同一個錯不要糾正第二次。** pstack 有一個 skill 叫 correct，它會去翻最近的 commit 跟 review，找出 agent 一直重複犯的錯，再照順序處理：最好是改架構，讓這個錯根本寫不出來；其次用型別或 lint 擋下來，lint 就是自動檢查寫法的規則；再來寫測試；寫成文件排最後，因為 agent 跳過一條文件規則，什麼都不會報錯。

做這支影片的專案，給 AI 看的說明檔裡就有一張表：左邊是規則，右邊是誰擋下來。像每一集的資料夾只准放三個檔，多放一個，檢查指令就直接失敗。AI 不必記得這條規則，違反的那一刻就會知道。

她還有一句話我很喜歡：一個無法驗證自己的迴圈，只會讓沒檢查過的工作變得更快。所以每抓到一個錯，修法要落進專案裡，變成架構、型別、lint 或測試，讓下一隻 agent 不會再犯同一個錯。

## 工具：Vitest、Playwright 跟驗證 skill

工具怎麼選？網頁專案的話，細的單元測試用 Vitest，小屋用的就是它；端到端用 Playwright，它可以開一個真的瀏覽器，照你寫的步驟去點。兩個都免費，程式也可以叫 AI 寫。

咒語大概是這樣：幫我用 Vitest 加測試，以後每修一個 bug，先寫一個會失敗的測試，修好再讓它變綠燈；再加一條 Playwright 測試，從首頁一路走到預約成功。拿那個預約網站試，上一篇那排 CI 的燈，就會多出這幾條。

這篇要介紹 pstack 的一個功能，叫 create verification skill。它會自己讀你的專案，替你的 app 寫一份驗證說明書：怎麼開起來、怎麼操作、怎麼留證據。最重要的是一張功能地圖，記下每個功能要從哪裡點進去、看到什麼才算過。

小屋 10 月 16 號加了一份驗證 skill，叫 verify-pa-cafe。現在地圖上有十幾個功能。像告示板那一份，就寫了怎麼新增、鎖定、重新整理後解鎖、刪除，關鍵的畫面要截圖，每一步還要從另一條路讀資料，核對真的有存進去。

app 會一直改，地圖也會過期，所以 pstack 還有一個 maintain verification skill，定期把地圖上的功能重走一遍。地圖跟現況對不上，就修地圖；如果是產品壞了，就照實回報。小屋這份驗證 skill，一個月內就改了七十幾次，跟著 app 一起變。

老實說，我自己 4 月也寫過一個類似的 skill。它會派 AI 扮成真實用戶，到產品的介面裡把流程走一遍，記下卡在哪：先跑固定的回歸流程，再自由逛，找使用上的問題。方向一樣，跟大神比，我少想了好幾件事。

- 我沒有功能地圖，每次 AI 都要自己摸索功能在哪。
- app 改了，我的 skill 沒有人維護，很快就跟不上。
- 我沒規定寫的人不能自己判過關，證據也沒規定要附可以重看的指令輸出跟截圖。

poteto 把這幾件事都做成固定步驟，所以她的驗證可以每天跑，換誰來跑結果都一樣。

## 我的看法：規格是轉譯

最後寫我自己的看法。這一兩年很流行一種做法，叫規格驅動開發，英文 spec driven development，簡稱 SDD：先把需求寫成一份很完整的規格，再叫 AI 照著規格寫程式。我本來就不支持，因為規格是轉譯。

你腦中有一個想要的東西，先轉成文字寫進規格；AI 讀了規格，再轉成程式。每轉一手，都會走味。就像客人跟店員說，想要一杯不要太甜、但要有點焦糖味的拿鐵，店員寫成點單，咖啡師照點單做，最後那一杯，常常跟客人心裡想的差一截。

前陣子有一個很紅的 skill，叫 grill me，是 Matt Pocock 做的，他那套技能包在 GitHub 上有三十幾萬顆星。它會一直拷問你，問到需求清楚為止。我也被它拷問過兩個小時，寫出一份很完整的規格。照著做完，結果大錯特錯。

grill me 把需求問清楚，這一步很有用。問題出在只有規格、沒有驗證。我回頭想，只靠規格，會遇到三個問題。

**第一，規格沒人驗。** 點單寫得再仔細，咖啡做好沒人試喝，就不知道對不對。規格只是對需求的猜測，要真的做出來、從頭走過一遍，才知道猜得準不準。

**第二，規格會過期。** 菜單每週在改，點單範本還停在開幕那天。程式改到第十版，規格沒人跟著改，下一隻 agent 讀到的，就是過期的指示。測試就不會這樣：程式一改，測試沒跟上，CI 馬上亮紅燈，它沒辦法安安靜靜地過期。

**第三，規格切得越細，越容易歪樓。** 局部的規格，寫的是這一格要怎麼做；端到端，寫的是客人從點單到拿到咖啡要順。兩邊有衝突的時候，agent 會選寫得比較明確的那條，也就是局部規格，因為明確的條件好打勾，整體順不順很難判斷。結果每一格都打勾了，拼起來，卻不是客人要的那一杯。

所以我現在的做法，是一開始就把端到端釘住：用戶從哪裡進來、走完要看到什麼，才算做完。中間怎麼做，留彈性讓 agent 自己找路，最後用端到端驗證去對。這是我目前用起來整體比較順的做法，也還在一邊做一邊調。

我把這個做法寫成一個 skill，叫 walking skeleton，會走路的骨架。意思是先做一條最細、但從頭到尾都是真的路：真的用戶、從真的畫面進來、真的看到結果。這條路通了，再慢慢長肉：抽出共用的程式、補其他情境、補例外處理。

poteto 也講過類似的話。她在 pstack 的說明裡寫，她個人不相信規劃，最好的規格就是程式碼。我再補一句：測試就是會跑的規格。它寫的是成品該有的行為，程式一改就會被檢查一次，也不會悄悄過期。

所以 grill me 跟驗證可以一起用。還沒想清楚要做什麼的時候，用 grill me 把需求問清楚；需求清楚了，先釘住端到端的終點，再讓 agent 自己做、自己驗。

## 對 vibe coder 的好處

講了這麼多，對 vibe coder 有什麼好處？

1. **你敢改。** 有測試在，加新功能時舊功能壞了，會先亮紅燈，輪不到用戶發現。程式改到第十版，第一版的功能還好好的。
2. **你敢放手。** agent 交回來的東西附了證據：測試結果、截圖、跑過的紀錄。你不必每一行自己看，看證據、抽樣就好。
3. **同一個錯只錯一次。** 每踩一個坑，就補一個測試或一條檢查，下次不用你再講一遍，換哪一隻 bot 來改，都會被同一條規則擋下來。

## 做好了，證據呢？

回到開頭那個優惠券。AI 說做好了，測試全過，你現在知道要多問兩句：測了哪些？有沒有從用戶的角度，真的走過一遍付款？上線只是第一天，測試跟驗證，讓你之後的每一天都敢改。

這週回家，問你的 AI 三件事：

- 我的專案有沒有測試？
- 最重要的那條用戶路線，有沒有一條端到端測試？
- 下次你說做完了，可以給我看什麼證據？

裝了 pstack 的話，再跑一次 create verification skill，看它幫你的 app 畫出什麼地圖。
