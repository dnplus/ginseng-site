## 搶凱道路權在吵什麼？350 毫秒有多快？

每次台灣大選前一天晚上的「選前之夜」，總統府前的凱達格蘭大道都是各陣營最搶手的造勢黃金場地。台北市政府規定，想借路權的人必須在開放日午夜 00:00 準時上網「先搶先贏」。

這波爭議的起點，是這次午夜剛過 **0.350 秒**，凱道路權就被搶走了。沒搶到的陣營質疑：上網申請要填身分證字號、在電子地圖上點路段、還要填一整串資料，人類手速怎麼可能在半秒內填完，懷疑有人寫外掛甚至黑箱。另一邊，台北市政府新工處則公布歷年紀錄反擊：

| 年份 | 第一筆成功遞件時間 |
| --- | --- |
| 2020 | 0.630 秒 |
| 2022 | 0.380 秒 |
| 2024 | 0.330 秒 |
| 2026 | 0.350 秒 |

年年都在一秒以內完成遞件，社群瞬間炸鍋，許多工程師也跳出來拆解。但對一般吃瓜看熱鬧的讀者來說，最核心的問題其實是：**在電腦系統的時間軸裡，350 毫秒到底算不算快？**

要對速度有真正的感覺，最好的方式是把一條橫跨 **15 個數量級（$10^{15}$ 倍）** 的時間軸攤開：從以前跑紙本公文的幾天出發，一路加速穿過區公所櫃檯、自助網站、自動化腳本、網路協定，最後撞進處理器 **0.25 奈秒** 的電子世界。

## 數位化的五個速度階梯

| 階段 | 典型做法 | 時間量級 | 主要瓶頸 |
| --- | --- | --- | --- |
| 1. 全紙本公文 | 送件、排隊、蓋章、郵寄 | 數天（3 天 ≈ 259,200 秒） | 紙張與人走路的速度 |
| 2. 區公所臨櫃登打 | 後台已數位化，現場抽號碼牌由承辦人逐欄輸入 | 小半天／數小時（≈ 10,000 秒） | 現場排隊與人工窗口 |
| 3. 自助申辦網站 | 上網找表單、填欄位、傳附件、打驗證碼 | 數分～數十分鐘（$10^2$–$10^3$ 秒） | 人類的眼睛與雙手 |
| 4. 瀏覽器自動化 | Playwright 等腳本自動開網頁填表送出 | 數秒（$10^0$ 秒） | 前端渲染與介面步驟 |
| 5. 後台直打 API | 跳過整個瀏覽器畫面直接送請求封包 | 數十毫秒（$10^{-2}$ 秒） | 網路 RTT 與後端處理 |

走到第五層，才真正踏進凱道 350 毫秒這個區間。

## 拆解秒殺背後：表單、對時、握手與並行搶鎖

### 1. 為什麼「填 16 格資料」跟「0.35 秒」不在同一條尺上？

對照「臺北市申請使用道路網」的公開實測流程，人工走完一套申請需要 **11 個步驟、填寫 16 格資料**，包含在電子地圖上點選路段與方位、填寫聯絡資料、6 格保證金退款帳戶以及系統驗證。質疑「不可能 0.35 秒填完」聽起來很合理，因為背後套用的是**人類操作自助網頁的量級**。

在許多線上申請系統裡，常見的結構風險出在把關卡做在前端——例如 00:00 之前鎖住日期不讓人點選。但如果後端沒有把驗證碼與一次性 token 嚴格綁死，只要腳本提前摸清楚送單的 API 參數格式，把身分證、路段代碼、六格銀行帳號寫進請求裡，00:00 一到直接發送 `POST` 封包，前面 11 個步驟與點地圖就能全部跳過。

### 2. 時鐘偏移（Clock Drift）與 NTP 對時

很多人直覺會問：那我盯著手機時間，00:00:00 準時按下去不就好了？

實際上，你的手機跟政府機房的時鐘本來就可能差個幾十到幾百毫秒（Clock Drift），加上封包從你家飛到機房還要一段單程傳輸時間（$\frac{1}{2}$ RTT）。等你眼睛看到 00:00 才按下手指，封包飛到機房早就慢半拍。專業搶票腳本會先用 **NTP（RFC 5905）** 校準時間，再估算單程延遲，提前幾十毫秒發射封包。

### 3. 實務網路環境的 HTTPS 握手成本

台灣本島光纖跑一趟來回（1 RTT）實務上大約 **10 到 30 毫秒**，跨電信或尖峰可能拉到 50 毫秒。如果 00:00 才建立一條全新的 HTTPS 連線：

- TCP 三向交握：1 RTT
- TLS 1.3 加密握手：1 RTT（舊版 TLS 1.2 需 2 RTT）

還沒開始傳送表單資料，光建立連線就先吃掉 **20 到 100 毫秒**。但如果在 23:59:59 先把連線預熱建好、維持 **Keep-Alive** 長連線，00:00:00 一到就能以 **0 毫秒握手成本** 直接把表單封包送進伺服器大門。

### 4. 並行搶鎖與資料庫序列化

0.350 秒不只是單一請求的時間，午夜零點一到，幾十上百個並行請求會同時撞進同一台伺服器。伺服器核心數有限，連線得先在排隊隊列裡等待；進到資料庫後，為了確保同一塊場地不會重複核准給兩個人，資料庫必須透過交易鎖（Row Lock）把所有並行寫入強制排成一列序列化執行。

這也是為什麼搶演唱會門票或搶路權在 00:00 總是開始轉圈圈。0.350 秒裡已經包含封包排隊、驗權、搶鎖到第一筆寫入完成。

## AI Agent 的四層速度階梯，與 LLM 為什麼搶不贏腳本

同樣叫程式幫你操作電腦，換不同介面速度直接差了一千倍：

1. **Computer Use（2–10 秒／步）**：每一步都要截圖、看圖思考再決定滑鼠點擊位置，拿去搶路權連車尾燈都看不到。
2. **Browser Use（0.5–3 秒；純腳本數百毫秒）**：直接讀網頁 DOM 結構，拿掉模型思考後可壓進幾百毫秒。
3. **HTTP REST API（10–100 毫秒）**：跳過瀏覽器引擎與畫面渲染，直接收發封包。
4. **WebSocket 長連線（1–20 毫秒）**：維持雙向常駐通道，免重連直接推播。

很多人好奇，為什麼跑在高階 GPU 上的 AI Agent 反而比一段陽春腳本慢幾百倍？關鍵卡在**記憶體頻寬（Memory-Bandwidth Bound）**：大語言模型每吐出一個字，都得把幾百億個參數從顯卡記憶體搬進運算核心算一遍，加上首字延遲（TTFT）動輒 300 到 1,000 毫秒。從硬體本質上，它就跟 10 毫秒的純程式碼屬於完全不同的量級。

## 穿過協定與光纖，直衝亞奈秒

### TCP + TLS vs QUIC（HTTP/3）

現代的 **QUIC（RFC 9000）** 把傳輸與加密握手合併，壓成 1-RTT 甚至 0-RTT，並跑在 UDP 上解決了 TCP 一掉封包整條連線卡住的隊頭阻塞（Head-of-Line Blocking）問題。但工程世界沒有白吃的午餐：0-RTT 因為在完整確認前就送出資料，帶有**重放攻擊（Replay Attack）**的資安風險，因此實務上多半只開放給純查詢請求，牽涉扣款或搶路權下單仍得老實走完驗證。

### Google Abseil 官方延遲表：全部對齊奈秒（ns）

把 Google Abseil 工程團隊整理的經典延遲數據統一換算成奈秒右對齊，再把「1 奈秒放大成 1 秒鐘」換算成人類時間感，差距瞬間一清二楚：

| 動作 | 真實時間（對齊 ns） | 若 1 ns = 1 秒（人類時間感） |
| --- | --- | --- |
| CPU L1 Cache 讀取 | 0.5 ns | 0.5 秒（伸手就拿到） |
| 無競爭 Mutex Lock / Unlock | 15 ns | 15 秒 |
| 主記憶體 RAM 存取 | 50 ns | 50 秒（去隔壁房拿） |
| SSD 隨機讀取 4 KB | 20,000 ns | 5.5 小時（高鐵來回） |
| 同資料中心內部網路來回 | 50,000 ns | 13.9 小時 |
| 跨大西洋 CA → 荷蘭 → CA | 150,000,000 ns | 4.75 年（大學都畢業了） |
| **凱道搶路權紀錄（350 ms）** | **350,000,000 ns** | **11.1 年（小學一年級讀到高二）** |

最後進到晶片核心：一顆 **4 GHz** 的處理器，一個時脈週期只有 **0.25 奈秒**，電晶體開關更掉進數十皮秒。在 1 奈秒裡，連宇宙最快的光都只前進約 **30 公分**（桌上那把長尺的長度）。新聞裡吵翻天的 350 毫秒，已經夠這顆處理器跳完 **14 億個週期**。

## 回到凱道，與 Vibe Coding 時代的基本功

回到開頭的問題：**在電腦系統的時間軸裡，350 毫秒到底算不算快？**

答案是：在電腦系統裡，它其實慢到不行。跟人類比，它快過你眨一次眼；跟後端系統比，它慢到處理器已經跑完 14 億個週期，換算成人類時間等於乾等 11 年。當一套制度從紙本三天進化到毫秒級，卻還維持「誰先按到算誰的」規則，就等於逼人類 250 毫秒的神經反應，去跟預熱長連線的 10 毫秒程式對撞。與其每年猜誰寫外掛，把熱門路權改成「截止後公開抽籤」，直接把時間軸從規則裡抽掉，才是工程上真正的解法。

最後想多講一句給正在寫程式的朋友：現在靠 **Vibe Coding**，把一個系統從 **0 到 1** 做出來變得很簡單，過去這一步超級困難。但任何系統都少不了外部相依，套件與雲端幫你把複雜度封裝起來了，水面底下每一層網路握手、並行搶鎖、記憶體快取與延遲成本，從來就沒有憑空消失。它們全是幾十年累積出來的底層，每一毫秒都有代價。從 **1 到 99** 的眉角靠的是親手做過、身體力行，AI 只能當輔助——**你連自己不知道什麼都不知道，是要怎麼問 AI，對吧？**
