PA Cafe，也就是 PA 小屋，是我做給 personal bot 協作的空間。我這間屋子裡有幾位幕僚長，也就是負責不同工作的 bot：它們互相傳訊息、接任務，有事發生時，小屋會叫醒負責的那一隻。這次把小屋架上線，我也是和 Grok bot 一起做的。

前幾集聊小屋怎麼用，這集往底下看：資料放哪裡、周邊服務怎麼接、agent 怎麼部署、誰能動正式站，以及費用怎麼算。

## 先看使用情境與部署全圖

我在網頁派一個任務，幕僚長收到通知，在自己的執行環境工作，再把結果送回小屋。其他幕僚長和我打開網頁，都要看到同一份進度。小屋負責記錄、協調和送出更新；bot 的工作環境可以分開部署。

人從瀏覽器進來，bot 透過 MCP 呼叫工具，前面由 Cloudflare Worker 接住。Worker 就是雲端幫我執行的程式。後面每間小屋各有一個 Durable Object，存自己的訊息、任務與狀態；圖片放 R2。

這樣拆，是因為同一間屋子的資料常常一起更新，圖片則適合放在專門的檔案儲存。網頁和 bot 共用入口，方便一起部署與維護。

另外兩個服務放在 Cloudflare 外面：登入交給 Clerk，Worker 只負責驗使用者帶來的通行證，也就是 token；收錢交給 Polar，付款結果由 Polar 主動打過來通知 Worker，這叫 webhook。

## 動手前，先讓 agent 接上 Cloudflare

Claude Code、Codex、Grok bot 這些 coding agent 的外掛市集裡都有 Cloudflare。先把它接上去，agent 就有 Cloudflare 的 skill，也能透過它的 MCP 呼叫 API。開資源、看 log、查用量，這些事 bot 都可以代勞。

Cloudflare 的基本概念還是要自己懂。後面的東西不少，看一次不一定記得住，可以邊做邊問你的 bot：這個東西是怎麼運作的？

## 先從一個 Worker 開始

PA 小屋的網頁、API 和 MCP 入口，都由同一個 Worker 接。網域綁在 Worker 上，DNS 和憑證交給 Cloudflare 管。

免費方案每天十萬次請求，每次請求的 CPU 時間上限是 10 毫秒。CPU 時間只算程式真的在跑的時間，等資料庫、等外部 API 回來都不算。

前端是單頁式網頁，沒對到的路徑預設會回到首頁。MCP 若也被這個規則接走，bot 會拿到網頁。因此設定裡要明列 API、MCP、OAuth、媒體等路徑，先交給 Worker 處理。

設定檔裡的相容日期（compatibility date），可以想成把規則鎖在某一天：Cloudflare 之後改了某個功能的行為，程式還是照那天的規則跑；自己改日期，才換成新規則。有些行為也能用旗標單獨開關。我升級時就改日期、跑測試，再上線。

## D1、KV、Durable Objects：先看資料長什麼樣子

D1 像中央檔案室，適合用 SQL 跨表查詢、整理報表。KV 像名字對應值的小抽屜，適合放設定和快取；剛改完的值，別的地方可能暫時讀到舊版，所以要先想這份資料晚一點同步能不能接受。

那聊天室這種要即時的東西呢？D1 也能把狀態存成一張表，但它只會記，不會動：有新訊息時，它沒辦法主動通知誰，大家只能一直回來問「有沒有新的？」，問一次就是一次請求。Worker 本身沒有記憶，A 連到的實例和 B 連到的實例，彼此找不到對方。

Durable Objects 把一段一直在的程式放在資料旁邊。同一個名字永遠找到同一個物件，大家的連線都接在這裡，有新訊息它直接推出去；沒事就休眠，時間到了還能靠鬧鐘自己醒來。每個物件有自己的儲存空間，可以放一顆 SQLite，同一時間只有一個活躍實例。

用 PA Cafe 舉例：兩隻 bot 同時想接同一個任務，這間屋子的 Durable Object 就像會議室的主持人，一個一個處理。先到的那隻在白板寫上「我接了」，第二隻來問，看到的就是已經有人接。

改完馬上讀得到，D1 也做得到。差別在主持人就坐在會議室裡：先看白板、判斷、再寫上去，判斷可以直接寫在程式裡；而且每間屋子各有一位主持人，各排各的隊。接任務要同時改任務狀態和負責人，這兩筆要包在同一個交易裡。程式等外部 API 時，其他請求還是可能進來，所以需要一起完成的修改，仍要寫好交易與併發控制。

小屋天生是一間一間的，所以我選 Durable Objects：一屋一個物件，收進住民、任務、訊息、事件和叫醒排程。目錄另外記帳號、小屋與成員；來源登記處把外部通知導向正確的小屋。

新增一種物件類別要寫 migration。類別像會議室的設計圖，實例是照圖蓋出來的每一間：多蓋一間小屋，只是多一個實例；多一種設計圖，才要加 migration。刪類別會連資料一起刪，這類改動要讓人審查。

PA 小屋連 Cloudflare 的訊息排隊服務 Queues 都沒用。要送的事件先寫進屋子自己的資料庫當待辦，再靠 Durable Object 的鬧鐘送出。失敗會隔 5、20、80 秒重試，次數有上限，最後仍失敗也保留狀態。待辦先落地，就算 bot 剛好離線，通知也還在待辦簿上，晚點再送。

## 周邊服務各做各的事

圖片放 R2，直接從 R2 下載不收流量費；Workers AI 讓小模型先判斷通知是否需要廣播。工具呼叫有每分鐘 300 次的速率限制。Email Routing 接網域信件，管理入口由 Cloudflare Access 檢查身分，業務事件留給 Analytics Engine。

### 一般使用者的登入：Clerk

我比較過幾家，選 Clerk 有三個原因：

1. Google、LINE、X 都是內建的，台灣人很常用 LINE 登入。
2. 不用自己架登入服務，Worker 拿它給的公鑰，就能驗使用者帶來的 token。
3. 免費方案就夠用，還能接三種社群登入。

用下來發現它彈性滿大，候補名單 waitlist 也是內建的。我先用 waitlist，原因有兩個：Cloudflare 的費用還不太好預估；一下子全部開放，很多人同時遇到問題，我一個人也處理不來。用候補名單可以先抓大概會有多少人，再分批放行。等版本比較穩定，不用一天改那麼多版，再考慮開放直接登入。

### 收款：Polar

台灣的金流大多要做商家審查，還有基本費；Stripe 不支援台灣，個人開發者很難用。Clerk 也有訂閱收款的整合，但它只透過 Stripe 收款，所以我用不了，不然連 Polar 都不用接。

Polar 對開發者很友善，月繳、年繳、退款都有現成的；付款結果用 webhook 通知 Worker，測試用 sandbox，跟正式站分開。

### 設定與秘密

外部服務的設定，repo 裡只寫名稱與用途，真正的秘密另外用 wrangler secret 設進 Cloudflare。清單裡有真正的密鑰，也有本來就公開的識別值：像 Google 行事曆的 client ID 本來就公開，client secret 才是要藏好的秘密。

即時更新使用 WebSocket Hibernation。沒訊息時，連線保留、Durable Object 可以休眠。小屋目前每屋最多 32 條連線、每條最長一小時，心跳由 Cloudflare 自動回覆。

## 為什麼需要測試、預覽與正式環境？

production 是真的使用者正在操作的正式站，裡面有帳號、任務和訊息。功能持續修改時，需要 testing 這個測試空間，先用測試資料檢查新增、修改、刪除是否正常；測試可以先在本機做。

分支，就是改功能時另外開的一條線。preview 提供改動分支的預覽版，讓人或驗收 bot 直接進去操作。staging 則做上線前的整合演練，盡量接近正式站的運作方式，把登入、訊息與檔案等流程串起來測。各關抓不同問題，能降低正式上線才出錯的機會。

資料、登入、檔案空間和權限都要實際分開設定。PA Cafe 的本機用假資料；staging 有自己的 Worker、屋子資料與 R2 bucket。分支預覽另有自己的屋子資料，使用測試登入，也不接正式檔案空間。上線後仍要觀察錯誤紀錄，並準備回滾。

## 合併與發版，分成兩次核准

前面講的 Worker、儲存和資源綁定，大多寫在 Wrangler 設定檔裡。Wrangler 是 Cloudflare 的命令列工具。設定是文字，agent 看得懂、改得動，改了可以開 PR 給人看。

我的流程從需求開始：bot 開分支、本機測試、開 PR；CI 依變更範圍選受影響測試或整套測試。整套測試目前分成三份，交給 runner，也就是實際跑 CI 的機器。

分支先用預覽版驗收，需要整合測試就送 staging，驗過才合進 main。main 是整合好的程式，正式站另外走發版流程。驗收 bot 跑操作，管上線節奏的上線管家整理建議，真正要發版仍由我決定 release tag。

tag 就是幫某一個版本貼標籤，說這一版要上線。GitHub 先確認這個版本在 main 的歷史裡，也就是審過、合進來了；通過後才把 production 分支移過去，再由 Workers Builds 建置部署。同時間只跑一個發版。發完驗正式站，有問題由人決定如何回滾。

Cloudflare 的 CLI 和 MCP 可以查部署紀錄與 log。我踩過兩份設定檔內容不一致的坑：本機好好的，上線登入卻回 503。後來補齊設定，也加測試檢查應一致的欄位。部署時明確指定設定檔，agent 才知道上線讀哪份。

## CI 排隊，先解自己的問題

bot 常把工作拆成很多小 PR，每一個都跑 CI。當時我的私有 repo 帳號從每月 2,000 分鐘加購到 3,000 分鐘，還是用完。

我先拿家裡閒置的 NUC 跑 self-hosted runner。起初一個 runner 排很長，後來先開到三個。ARC 能用 Kubernetes 自動管理 runner，但為了這個規模去養一整套 Kubernetes，對當時的我像為了買菜買貨車。

Anthropic 的 Scion、Cloudflare 的 Artifacts 都在回應 agent 改動量增加後的開發工具問題。規模差很多，但方向值得觀察；自己的瓶頸仍要自己判斷。

## 權限要看真正能做什麼

發版流程有人核准，只是其中一層。token 就是給程式用的鑰匙：部署、清理、回報問題各用各的，還要核對它實際能操作哪些資源。把清理目標移到 staging Worker 底下之後，token 的資源範圍也要另外縮小。

來源 IP 限制（寫法叫 CIDR）是多一道檢查，但同一個網段裡，拿到這把 token 的機器都能用，所以權限範圍仍然要縮小。

秘密不進程式碼，預覽與正式資料分開。Worker 對外連線一律走公開網路，連到自己帳號底下的網站，也跟外人一樣從正門進；送出 webhook 前會檢查目的地，收到的 webhook 先檢查來源、大小和簽章。AI 掃描抓出的 webhook 重放判斷、驗簽前讀取沒有大小上限，都補了處理與測試。真的送攻擊請求驗證時，限定在 staging。

最後用人與 AI 交叉核對：它改的我看，我設的再讓它檢查。正式站權限與發版，最後由人決定。

## 費用試算：先算 Workers，再補其他服務

Cloudflare 的計費項目不少：請求、運算時間、資料庫讀寫、儲存量，各有自己的單位。流量與各項用量都不高時，包含額度常常就夠用，這也是「賽博菩薩」這個稱呼的由來。付費方案仍有固定月費。

想估得準，可以拿線上的 metrics，也就是實際用量數據，對照各項計價方式，再估每月費用。bot 可以幫忙整理與試算，自己也要知道哪些操作產生成本。看懂這些項目，才知道帳單從哪裡來。

以下價格核對日期為 2026-10-25，之後以官網為準。額度以整個帳號合計。

| 項目 | Workers Paid 每月包含 | 超額單價 |
| --- | --- | --- |
| 方案月費 | US$5 | — |
| 請求 | 1,000 萬次 | 每百萬次 US$0.30 |
| CPU | 3,000 萬毫秒 | 每百萬毫秒 US$0.02 |

等待外部 API 的時間不算 CPU。預設靜態資產請求免費；若另外啟用 Workers Caching，要依該功能的計價條件核對。

假設帳號沒有其他 Worker 用量，而且每次請求平均使用 5 ms CPU：

- 每月 300 萬次：CPU 共 1,500 萬 ms，兩項都在包含額度內。Workers 為 **US$5**。
- 每月 1,500 萬次：請求超出 500 萬次，加 US$1.50；CPU 共 7,500 萬 ms，超出 4,500 萬 ms，加 US$0.90。Workers 合計 **US$7.40**。

![Workers 月費試算：1,500 萬次請求及 7,500 萬 ms CPU](/blog/ep084/zh-TW-05.webp)
*Workers 月費試算：1,500 萬次請求及 7,500 萬 ms CPU*

這兩個數字只算 Workers。Durable Objects 活躍時間與讀寫、R2、AI 推論等要另外列。Durable Objects 每月包含 100 萬次請求及 40 萬 GB-s 執行時間，計價記憶體以 128 MB 計。Durable Objects 的 SQLite 與 D1 的包含額度為讀 250 億列、寫 5,000 萬列及 5 GB 儲存，超額儲存單價不同。

R2 Standard 有 10 GB 月儲存、100 萬次寫入類操作、1,000 萬次讀取類操作。Workers Logs 現行付費方案包含 2,000 萬筆、保留七天；官方已公告 2026-12-01 改用 Observability 計價，估算時要留意日期。

## 上線以後，持續看用量

Durable Object 若因 WebSocket 一直醒著，執行時間就會累積；使用官方休眠介面、連線數與時效限制，能避免不必要的活躍時間。bot 也可能卡在重試迴圈，所以 CPU 上限、速率限制與帳號總用量都要顧。

這次留下兩個原則：先看資料形狀，再選儲存；踩過的坑，寫成下一次會自動擋下的測試。下一集再把資安展開來講。
