## 寫得快，上線也要快

用 AI 寫程式，最大的改變是快。你想做一個預約網站，一個下午，預約頁、會員登入、付款按鈕就都做好了。

可是做完之後呢？每一頁都要自己點開來檢查、自己上線，還要擔心一上線，就把用戶正在用的服務弄壞。

CI/CD 就是把這一段交給機器：自動驗證、自動部署，線上還能穩穩的。這個詞工程師天天掛在嘴邊，剛開始用 AI 寫程式的人卻很少聽過，這篇就專門講它。

這是小屋技術白話課第四篇。第一篇講版本控制的時候，我說過下一篇往測試跟部署走，中間插了 API 跟資安兩篇，這次來兌現。一樣不用買課：每講一個詞，我就叫 bot 用 [pstack](https://github.com/cursor/plugins) 的 `teach` 拿小屋實際跑一次，你也可以用自己的 AI、拿自己的專案問一次。

## CI/CD 是什麼？用咖啡店講

開一家咖啡店。店裡有好幾個咖啡師，每個人都會改配方：有人調糖漿，有人換豆子，有人改拉花。改完的配方，最後都放回同一本配方書。

### CI：出餐前的品管台

![品管台：每杯咖啡出餐前先試做、試喝](/blog/ep097/qc-station.jpg)

CI（持續整合）是出餐前的品管台。每次有人改了配方，品管台就自動試做一杯、試喝一口：份量對不對、擺盤合不合規矩、味道有沒有走鐘。沒過就退回去重做，這杯不准出餐。

換成程式：

- 配方書是 GitHub 上的 `main`，也就是主線。
- 想改 `main`，要先開一個 PR，就是一張「我改好了，請檢查完再合進去」的申請單。
- PR 一開，CI 就自動跑檢查：寫法有沒有寫錯、格式合不合規矩、測試有沒有過。全過亮綠燈，有一項沒過亮紅燈。

為什麼叫「持續」？因為大家都往同一本配方書改。隔很久才合一次，每個人的改動會互相打架，合的那天最痛。所以做法是每次改小一點、常常合，每次合之前先自動檢查一次。持續，講的就是這個頻率。

### CD：一層一層往外送的送餐路線

![送餐路線：試吃員、員工餐，最後才上菜單](/blog/ep097/delivery-route.jpg)

CD（持續交付或持續部署）是送餐路線。品管過了，先給試吃員吃，再當員工餐吃一輪，大家都沒拉肚子，才放上菜單賣給客人。

| 咖啡店 | 程式 |
| --- | --- |
| 試吃員 | 每個 PR 的預覽網址 |
| 員工餐 | 測試站（staging） |
| 菜單 | 正式站（production） |

程式一層一層往外送，每一層都比上一層更靠近真的用戶。

### DevOps：一起負責到底

以前做軟體，寫程式的是一組人，顧機器、管上線的是另一組人。就像廚房做完菜就丟給外場，出了事兩邊互相怪。

DevOps 是一種做法：寫的人跟顧店的人一起負責到底，把做好跟上線接成同一條流水線。CI/CD 就是這條流水線上的機器。

### 小屋的 CI 在檢查什麼

我叫 bot 用 `teach` 問：小屋的 CI 在檢查什麼？它的回答整理起來：

- PR 一開，一整排檢查同時跑：型別、寫法、三份測試、覆蓋率。
- 結果最後匯到一個總閘 `all-checks`，有一項沒過就亮紅燈，照規矩不能合併。
- 很多測試是把以前踩過的坑寫成規則。例如程式用到的每個環境變數都要寫進設定檔；只在後台手動設的話，換個環境就不見了，CI 會直接亮紅燈。

## 寫得越快，越需要 CI/CD

![一個下午好幾隻 bot 同時開 PR](/blog/ep097/bot-rush.jpg)

以前一個人寫程式，一天改幾次，改完自己點一點就推上去。慢，但顧得來。

用 AI 之後就不一樣了。bot 一個下午可以開好幾個 PR，還可以好幾隻同時改。小屋 11 月前十天，就合併了一百二十多個 PR。一個只看五分鐘，十天也要十個小時。

這時候最常出三種事：

1. **改 A 壞 B**：叫 AI 改登入頁，結果付款按鈕壞了，用戶回報你才知道。
2. **我電腦上明明能跑**：一上線就掛。
3. **不知道是哪一次改壞的**：也不知道要退回哪一版。

這三種靠人盯很花時間，也盯不住。CI/CD 每一次都自動驗、自動部署，不會疲倦、不會偷懶。

## 工具：直接用 GitHub Actions

程式已經放在 GitHub 的話，直接用 GitHub Actions。它就在 GitHub 裡面，不用另外註冊。

- 公開的 repo，用標準機器免費。
- 私人 repo，免費方案每個月內含 12 美元額度，用標準 Linux 機器大約兩千分鐘。
- 兩千分鐘不夠用，可以拿自己的電腦來跑，這叫 self-hosted runner，用自己的機器不扣這個額度。

它就是 `.github/workflows` 資料夾裡的一個設定檔，寫什麼時候跑、跑在哪種機器、跑哪幾個步驟：

```yaml
on: pull_request
jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run typecheck
      - run: npm run lint
      - run: npm test
```

這個檔不用自己寫，叫 AI 寫就好：

```text
幫我加一個 GitHub Actions，PR 開了就檢查寫法、格式跟測試，
有一項沒過就讓 PR 亮紅燈。
```

幾件順便知道的事：

- **乾淨的新機器**：CI 每次都開一台新機器，照設定檔把套件從頭裝一遍。你電腦裡剛好有、設定檔裡卻沒寫的東西，在這裡會現形。這就順便解決了「我電腦上明明能跑」。
- **第一次常常一片紅**：老專案第一次加 CI，以前沒人發現的問題會一次翻出來。叫 AI 一條一條修到全綠，這排綠燈就是起點，之後每個改動都不能讓它變紅。
- **CI 能檢查多少，看你有多少測試**：沒有測試的專案，CI 只能檢查打字有沒有打錯。叫 AI 每修一個 bug 就補一個測試。小屋的 CI 還要求測試至少跑過 75% 的程式行數。
- **分支規則**：GitHub 可以規定 `main` 一定要等 CI 綠燈才能合併。公開 repo 免費，私人 repo 要付費方案。小屋是免費方案的私人 repo，所以「看燈再合併」是寫在流程裡、靠大家守規矩。
- **CD 更簡單**：Cloudflare 這類平台大多已經接好了，連上 GitHub，合併進 `main` 就自動部署，每個 PR 還會自動生預覽網址。
- **打包 app**：做的是要給人下載安裝的 app，GitHub Actions 有 Linux、Windows、mac 三種機器。你在 mac 上開發，也能叫它包出 Windows 的安裝檔。mac 的機器比較貴，私人 repo 會用掉比較多額度。

## 拿小屋走一遍：一個改動從 PR 到上線

| 站 | 小屋實際發生的事 |
| --- | --- |
| 1. PR 一開就跑 CI | bot 把額度卡上的小頭像改畫每隻 bot 自己的臉，CI 亮紅燈：舊的測試資料裡沒有角色資料。bot 自己讀錯誤訊息、補上測試資料，第二次全綠才合併。我一行都沒碰，也沒有用戶看到壞掉的設定頁。 |
| 2. 預覽網址 | 每個 PR 自動生一個網址，合併前就能點進去試。 |
| 3. 測試站 | 合併進 `main`，大約一分鐘就部署到測試站。測試站有自己的資料庫，亂試也碰不到真的用戶的小屋。 |
| 4. 正式站 | 要上線得打一個日期版號，像 `v2026.11.08.1`。好幾個 PR 可以在測試站累積一陣子，看過再一起上。 |
| 5. 萬一壞了 | 對舊的那一版打一個新的版號，正式站就換回去。 |

為什麼合併進 `main` 只更新測試站？`teach` 的回答很清楚：合併，是程式寫好、審過了；上線，是我決定這一批改動可以給用戶用。這是兩個分開的決定。

11 月 8 號那天很有代表性：早上 9:28 發第一版，發現好幾隻 bot 同時連線會被擋掉，修好合併，9:41 發第二版；還有漏網的情況，再修一次，10:24 發第三版。一小時出三版，每一版都過同一套檢查，走同一條路。

老實講，紅燈的原因有兩種。小屋最近兩百次檢查有十八次紅燈：四次是真的有測試沒過，另外十四次是 GitHub 給的存檔空間用滿，最後上傳紀錄那一步失敗。所以每個紅燈都點進去看一眼原因，別一紅就按再跑一次。

## 把資安塞進流水線：DevSecOps

![上游送進來的套件、映像檔](/blog/ep097/upstream-dock.jpg)

你的 app 裡，很大一部分程式碼是別人寫的。套件、框架，還有別人打包好的整套軟體（映像檔），都是你的上游；用你 app 的用戶，是你的下游。上游一出事，你的產品跟著出事，用戶找的是你。

DevSecOps 就是把資安塞進同一條流水線：除了檢查你自己寫的，也檢查上游送進來的東西。

### 上游真的會出事

- **Log4Shell（2021 年底）**：Log4j 是一個幫程式寫紀錄的小套件，一大堆 Java 程式都在用。攻擊者只要讓你的程式記下一行特製的文字，就能在你的機器上跑他的程式。很多公司根本不知道自己有用到，因為它藏在套件裡的套件。
- **xz 後門（2024 年 3 月）**：xz 是 Linux 上的壓縮工具，原作者一個人維護，早就忙不過來。一個叫 Jia Tan 的帳號從 2021 年開始熱心幫忙，花一年多取得信任、當上共同維護者，再過一年多才把後門放進去。後來是一位工程師發現 SSH 登入變慢了一點，追下去才抓到，那時後門只進了少數搶先測試的 Linux 版本。
- **AI 讓維護者更審不完**：curl 是幾乎每台電腦都有的下載工具。它的維護者 2025 年抱怨 AI 生的假漏洞回報多到像被灌爆，2026 年初乾脆收掉漏洞獎金。審不完，就可能漏掉像 xz 那樣的東西。

所以不能只靠上游把關，自己的流水線也要檢查。那為什麼不乾脆都不升級？不升級，舊的漏洞一直留著；亂升級，新的問題直接進門。檢查的目的是讓你敢升級：每次升級都過同一排關卡，有問題的那一版，合併前就亮紅燈。

### 一隻接上游專案的 bot 怎麼設關卡

我最近在公司幫同事架一隻打雜 bot，核心是一個開源專案，我再加自己的修改。這種接別人專案的架法，最需要檢查上游。

| 關卡 | 做法 |
| --- | --- |
| 1. 鎖門 | 主線不准直接推，所有改動開合併請求，檢查全過才能合併；合併後自動部署測試站，正式站只從版號上線。 |
| 2. 鎖上游身分 | 映像檔不寫 `16` 這種標籤，改記一串指紋（digest）。內容一變，指紋就對不上，CI 直接失敗。 |
| 3. 掃漏洞 | 用 Trivy 掃映像檔，只擋這次升級新帶進來、而且已有修補版的嚴重漏洞，結果留言回合併請求；每週一早上再固定掃一次。 |
| 4. 升級前先審 | 一套給 AI 的固定指示：升級前先讀上游這次改了什麼，把要注意的地方標出來。最近一次升級一口氣多了 407 個改動，人讀不完。 |
| 5. 下游遮罩 | 呼叫外部模型之前，個資先換成代號，每次呼叫都留紀錄。 |

為什麼只擋新的漏洞？第一次掃就翻出一堆早就存在的舊漏洞，評估過大多可以先不修。全部都擋的話，CI 第一天就天天紅燈，大家很快學會無視它，那跟沒裝一樣。舊的排進維護，新的當場擋。

標籤真的被換過。2025 年 3 月，GitHub 上很多人用的 Action `tj-actions` 被入侵，攻擊者把它的版本標籤全部改指到惡意程式，用它的 repo 超過兩萬三千個，CI 一跑就可能把金鑰印進公開 repo 的紀錄。Action 也一樣，用完整的 commit 指紋釘住版本，就不會被換掉。

### 你的專案可以先做的

- **開 Dependabot**：GitHub 內建的套件漏洞提醒。小屋 10 月 25 號一次收到六筆，四筆高風險，現在都修好了。
- **安裝腳本白名單**：套件可以在安裝的那一刻偷偷執行程式。2025 年 9 月，npm（JavaScript 的套件商店）上就有一隻蠕蟲用安裝時自動執行的腳本偷走開發者的金鑰，美國資安機關 CISA 說超過五百個套件中招。我另一個專案的做法是開一張白名單，只有名單上的幾個套件安裝時可以執行程式。
- **秘密不進程式碼**：金鑰和密碼放平台的保險箱，程式裡只寫名字。小屋的 CI 會檢查程式用到的每個秘密都登記在清單上。

自己查，光讀上游改了什麼就是一個下午；交給機器，每個 PR 幾分鐘就查完。

## 有了 CI/CD，vibe coder 可以怎麼做

1. **先看那排燈**：綠燈代表你定的規矩都守住了；紅燈點進去，會告訴你是哪一條沒過。
2. **放手讓 bot 一直改**：小屋平均每天合併十幾個 PR。改壞的在合併前被抓出來，漏網的因為有版號、有紀錄，一小時內就修完。
3. **bot 自己看得懂紅燈**：AI 改、機器驗、AI 再修，你只要決定什麼時候上線。
4. **出事有路可退**：每一版都有版號，退回去只要一個動作。
5. **規矩寫一次**：在對話裡交代 AI 的事，它下次可能就忘了；寫成 CI 的檢查，每個 PR 都會跑一次，換哪隻 bot 來改都一樣。
