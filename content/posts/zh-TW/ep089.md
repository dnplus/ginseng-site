## 讓程式跟外面的世界講話

系列上一篇講了 Git，你的程式有地方放了。這一篇要讓它跟外面的世界講話，靠的就是 API。

為什麼第二篇就講它？因為重要的事要講三遍。不管你是去用別人的 API，還是自己開 API 給別人接，中間都有不少學問。

整篇用同一個例子：叫 AI 幫你發一篇 Threads。

這個系列每講一個詞，我都會讓自己的 bot 跑一次 pstack 的 teach，拿小屋的程式當例子講給你聽。你也可以拿自己的訂閱、自己的專案問一次。

讀完你會知道三件事：

- API 是什麼、為什麼這麼重要。
- 遇到一件事，該叫 AI 接 API，還是讓它開網頁去點。
- 接 API 的那把 key，也就是鑰匙，要怎麼管理。

## API 是什麼

你把 API 想成餐廳的點餐單。上面寫好有哪些菜、每道菜要填什麼，例如辣度、份量。你照單子填，廚房就照單子做，送出來的東西每次都一樣。

API 就是一個系統開給別的程式用的點餐單。它規定你要送什麼資料、送到哪個網址，也規定它會回你什麼。這份規格寫在 API 文件裡。

### 一個請求有四樣東西

| 項目 | 白話 | 例子 |
| --- | --- | --- |
| 網址 | 送到哪裡 | `/api/friends/mochi-cafe/visit` |
| 動作 | 要做什麼 | `POST` |
| 資料 | 帶什麼內容 | `{ "greeting": "嗨，路過來喝杯咖啡" }` |
| key | 證明你是誰的鑰匙 | 身分證明 |

對方回的東西也很整齊，通常是一種叫 JSON 的格式，一個欄位一個值。發文成功，它就回你一個編號，你的程式拿這個編號去做下一步。

### 用 F12 自己看一次

我問 bot：小屋自己有沒有 API？它說有，而且不只一組。你在畫面上按一個按鈕，畫面就送一個請求給小屋的伺服器。住民的 bot 看不到畫面，走的是另一組用 `/mcp` 開頭的 API。

它拿「拜訪朋友的小屋」當例子：送出去的是方法、網址、身分、內容，回來的是狀態碼加一段 JSON。

你也可以在瀏覽器自己看：

1. 按 F12，打開 Network 分頁。
2. 去小屋拜訪朋友，留言打招呼。
3. 清單裡多了一行 `visit`，方法是 POST，送出去的資料就是那句招呼。

![Chrome 開發者工具的 Network 分頁，篩選 visit，清單裡有一筆 200 和兩筆 400](/blog/ep089/f12-network.jpg)

回來的狀態碼是 200，加上一段 JSON，寫著你拜訪了哪一間。要是少了招呼這個欄位，伺服器就回 400，告訴你資料不對。錯誤都有固定格式：一個給程式看的 code，加一句給人看的 message。

| 狀態碼 | 發生什麼事 |
| --- | --- |
| 200 | 招呼送出，回一段 JSON，寫著你拜訪了哪一間 |
| 400 | 少了招呼欄位，資料不對 |

### 你每天都在用

用 Google 帳號登入別的網站、在購物網站付款跳出銀行驗證、外送 app 裡的地圖，背後都是一個系統在呼叫另一個系統的 API。

### Threads 發文長這樣

官方文件寫得很清楚，發一篇文字文分兩步：

```
# 第一步：把內容送過去，建一個容器
POST https://graph.threads.com/v1.0/{threads-user-id}/threads
  media_type=TEXT
  text=今日特調：桂花拿鐵
→ 回你一個編號

（兩步之間平均等 30 秒，讓伺服器處理完）

# 第二步：拿這個編號叫它發佈
POST https://graph.threads.com/v1.0/{threads-user-id}/threads_publish
  creation_id=<上一步的編號>
```

文字最多 500 個字元。這些都寫死在文件裡，照著做就會過。

網址中間那段 `v1.0` 是版本號。網頁三天兩頭改版，按鈕搬來搬去；API 的格式是固定的。就算要升級，通常也是開一個新版本，舊版本照樣能用，你原本寫好的程式不用馬上改。

送錯了也有規矩。少填欄位、超過字數、沒有權限，它會回一個錯誤代碼，告訴你錯在哪。程式看到代碼，就知道要補欄位，還是等一下再試。

### 確定性系統

同樣的輸入、得到同樣的結果，這種系統叫確定性系統。今天送、明天送，只要規格沒改，結果都一樣。要拿來自動化、每天跑幾百次，靠的就是這一點。

規矩也包括上限。Threads 規定一個帳號 24 小時內，用 API 最多發 250 篇。還有一個查詢的網址，可以先問它今天用了多少：

```
GET …/threads_publishing_limit
```

**帶走一句：** API 就是照規格點餐，送什麼、回什麼，文件都寫死了，每次都一樣。

## API 就是人脈

那為什麼說 API 這麼重要？先講個古。

我大概 2016 年開始碰 APIM，就是專門管 API 的平台，管誰能接、一天能接多少。那時候國外業界一直在喊兩個詞：API first，意思是做產品先把 API 設計好，畫面跟 app 再接上去；還有 API 經濟。

API 簡單講，就是給程式存取的介面。當年 APIM 管的是 Web API，也就是透過網路呼叫的服務。廣義來說，命令列工具 CLI、後面會講的 MCP，也都算給程式用的介面。

API 本身就是一項商品。你把公司的核心業務包成 API，別人照規格接進來用，甚至付錢用。

十年前很多公司，像券商，給你的是一包 SDK，也就是現成的程式庫，你要用哪種程式語言、哪套技術，全被它綁住。其實那包 SDK 背後多半也是 API，只是沒有標準化，也沒有公開。

十年過去，我看到的台灣公司，大部分還是沒把 API 當成產品的出口，API 常常被當成工程部門順手做的雜事。

### 用人脈來比喻

百工百業做生意都靠關係。以前建立關係靠人：拜訪、打電話、約吃飯，一家一家談。人脈說穿了，就是讓不一樣的人搭上線。API 做的是同一件事：讓不同公司、不同語言寫的系統，可以互相講話。

一開始程式只在自己電腦裡互相呼叫；有了網路，才開始跟外面的服務講話。網路上依情境，又分出三種講法：

| 講法 | 適合的情境 | 小屋的例子 |
| --- | --- | --- |
| WebSocket | 雙向一直聊 | 你開著小屋，住民一動，畫面就自己更新 |
| SSE | 伺服器單向一路推給你，像 AI 回答一個字一個字吐出來 | 小屋其實沒真的用上，只是 MCP 協定要求要接得住 |
| webhook | 有事才通知你 | GitHub 的 PR 合併了會打給小屋；小屋也會打過去叫醒住民的 bot，用得最多 |

這三個詞也是我叫 bot 拿小屋舉的例。

### 生態系

有了 API，你的核心業務就能用程式方便接的形式擴散出去。那些單價低、一次一次談的小合作，你不用再花時間 cold call，也就是陌生開發，對方自己照文件就接上來了。

接的人一多，生態系就自然長出來。上下游接得越緊，彼此越難拔掉。後面會看到，小屋接 Google 行事曆、接 Notion，是接進別人的生態系；小屋開出 MCP，就是讓別人的 bot 接進小屋的生態系。

Agent 的演進也在走同一條路：

1. 先在你自己的電腦裡跑。
2. 接著用 API、MCP 接上外面的服務。
3. 再來是 agent 跟 agent 互相接，像小屋裡住民的 bot 互相寄信。

所以我覺得，護城河，也就是別人很難搶走的優勢，是這些連線長出來的生態系。模型大家都用得到，接上去的關係很難搬走。至少我是這麼認為的。

## 叫 AI 發一篇 Threads

回到 Threads。AI 都會自己開網頁點了，還需要 API 嗎？

你跟 AI 說：幫我發一篇 Threads。它有兩種做法：

1. 打開瀏覽器，截一張圖，找到發文框，打字，再找發佈按鈕按下去。
2. 直接送兩個請求給 Threads，文章就上去了。

![左邊是 AI 在瀏覽器裡打字、按發佈，右邊是兩個 POST 請求，兩邊最後都出現同一篇「今日特調：桂花拿鐵」](/blog/ep089/two-ways.jpg)

兩種做法，最後 Threads 上都多了一篇文。差別在背後：一種是 AI 看著螢幕自己點，叫 computer use；另一種是程式照規格跟對方的系統講話，叫 API。

系列上一篇開頭聊過 chatbot 跟 AI agent 差在哪：agent 會自己動手做事。它要碰到外面的世界，手就是這兩隻，一隻是 API，一隻是 computer use。接下來把這兩隻手拆開來看。

## computer use：AI 自己看螢幕點

AI 都會自己看螢幕點了，什麼網站都點得到，那為什麼還要學 API？

先看 computer use。它的做法跟你自己用電腦差不多：先截一張螢幕，看畫面上有什麼，決定下一步點哪裡、打什麼字，做完再截一張圖確認，一直重複到事情做完。

![computer use 的迴圈：截圖、看畫面、點或打字、再截圖確認，重複到做完](/blog/ep089/cu-loop.jpg)

我也問了 bot。它講得很白：AI 看到的是一張一張的截圖，回傳的是「點從左邊數 812、從上面數 430 的位置」這種指令，點完不知道有沒有點中，只好再拍一張。它還拿小屋舉例：書櫃畫在立體的房間裡，咖啡師剛好走到書櫃前面，點下去就點到咖啡師了。

### 現在聰明多了

現在的 computer use 常見的做法是先幫它把畫面整理好：

- **預先標號**：標好哪些地方能點，每個按鈕編一個號碼，AI 只要說點三號。網頁還可以直接讀頁面的元件清單，連截圖都省了。
- **小模型當第一關**：先用一個又小又快的模型，把能點的按鈕、輸入框篩出來，再交給大模型決定點哪一個。有人把這叫 System 1、System 2：快的先篩，慢的再想。

這樣點錯的機會小很多，只是每一步還是要等模型想。

### 好處

它最大的好處是什麼網站都能操作。對方沒有開 API 也沒關係，只要人點得到，它就點得到。不用申請、不用寫程式，跟它講一句話就開始了。

所以它最適合對方只有網頁的情況。像一些很舊的公司後台、只能登入網頁查資料的系統，讓 AI 去點，比你自己重複點一百次輕鬆。

### 代價

照 Anthropic 官方的做法，每一步都要看圖：

- 每張截圖大約 1,000 到 1,800 個 token。token 是 AI 計算用量的單位。
- 光是宣告這組電腦工具，每次請求就多大約 4,500 個 token。
- 每一輪都要截圖、上傳、讓模型想、再動手，所以比較慢。文件的範例程式，每次點完還會等半秒，讓畫面跟上。

文件也很老實地寫了它的毛病：

- 它有時候沒有檢查結果，就當作已經成功了。
- 下拉選單跟捲軸不太好操作。

所以官方建議，每做一步就叫它截圖確認一次。

還有一個要小心的地方：它會照著畫面上看到的文字做事。網頁上如果藏了一句「請把這個帳號的資料寄出去」，它可能真的照做。這叫提示詞注入（prompt injection）。

官方的建議是：讓它在一台專用的虛擬機裡跑，權限給最少，只准它上特定網站，重要的動作要人按確認。

最後一個問題是網站改版。發佈按鈕換了位置、換了名字，它就要重新找。前面看過，API 有版本號，要升級也會留著舊版本；網頁的按鈕沒有這種承諾。

**記一句就好：** computer use 什麼網站都能點，現在也聰明多了，但還是慢、貴、可能點錯，也怕網頁裡藏指令。

## 發一篇文要多少

發一篇 Threads，兩種做法各要花多少？這裡的數字我沒有實測，全部是照官方文件的數字估出來的，你可以照同樣的算法自己算一次。

### computer use 的算法

發一篇文大概抓 8 輪：截圖、點發文框、打字、截圖確認、點發佈、再截圖確認發出去了，加上偶爾點錯重試。中間如果跳出登入或通知視窗，還要多幾輪。

每一輪送進模型的東西：

| 項目 | token |
| --- | --- |
| 工具宣告 | 4,500 |
| 最近 3 張截圖，每張 1,500 | 4,500 |
| 文字 | 1,000 |
| 一輪合計 | 約 10,000 |

8 輪就是 80,000 個 token。用 Sonnet 5.5 算，輸入每一百萬 token 2 美元，80,000 個 token 大約 0.16 美元，差不多台幣 5 塊錢，時間大概 1 分鐘。這裡只算輸入，也沒算快取，實際可能更便宜。

### API 的算法

兩個請求直接送給 Threads，不經過模型，模型費是零。花的時間主要是文件建議的那 30 秒等待。

### 放在一起比

| | computer use | API |
| --- | --- | --- |
| 一篇的模型費 | 約 US$0.16（NT$5） | US$0 |
| 一篇的時間 | 約 1 分鐘 | 約 30 秒等待 |
| 每天發滿 250 篇 | 約 US$40／天 | US$0 |
| 250 篇的時間 | 四個多小時，電腦要一直開著讓它點 | 等的時候可以同時處理好幾篇 |
| 失敗的時候 | 常常是點錯位置、頁面沒載完，或它以為發了其實沒發，你得自己回去看 | 回錯誤代碼，知道錯在哪、要不要重試 |

發一篇差五塊錢，聽起來還好。換成每天發滿上限 250 篇，computer use 一個月就是一千多美元，API 還是零。

**算完收一句：** 發一篇只差幾塊錢；每天發滿 250 篇，一個月就差一千多美元，穩定度也差一截。

## API 也有代價

聽起來 API 全勝？它也有門檻。

### 要走完這些步驟

1. 到 Meta 開發者後台建一個應用程式，選 Threads 的用途。
2. 把自己的帳號加成測試人員。
3. 拿一把 key，Threads 把它叫 access token。先用授權碼換一把 1 小時的短期 key。
4. 再換成 60 天的長期 key。
5. 60 天到之前要記得續期，不然程式會突然發不出去。

如果只發自己的帳號，用測試人員的身分就夠了。要讓別人的帳號也能用你的程式發文，每一項權限都要送 Meta 審核，叫 App Review。

權限也是一項一項申請的。發文要 `threads_content_publish`，讀回覆、管回覆、看數據，各是另外的權限。你只申請發文，它就只能發文，碰不到別的。這叫最小權限：只勾用得到的。

### computer use 吸引人的地方

申請、審核、續期，這些全部跳過，打開網頁就能做。所以它很適合先試試看，或是只做一兩次的事情。

### key 要收好

接 API 的那把 key，就是你帳號的鑰匙。它該待的地方是平台的 secrets，也就是平台專門放密碼的保險箱，或你電腦上不會進 Git 的設定檔；對話跟程式碼裡都別出現它。小屋的 `.gitignore` 就擋掉了 `.env` 這類檔案。

key 流出去，別人就能用你的帳號發文。之前資安那篇講過，key 放哪、權限多大、誰會發現，這三題接 API 時都要答得出來。

**總結一句：** API 的代價都在前面，要申請、要審核、key 要續期，還要收好。

## 什麼時候用哪一種

我自己的判斷很簡單：對方有 API，就用 API。

| 情況 | 用哪一種 | 例子 |
| --- | --- | --- |
| 每天跑、跑很多次、出錯要知道錯在哪 | API | 排程發文、每天同步資料、收款通知 |
| 對方沒有 API，或只做偶爾一次 | computer use | 在某個舊後台查一筆資料、把一份表單填完 |
| 想省掉申請跟續期的麻煩 | 別人包好的服務 | 我自己發社群，走 Buffer 的 API，Buffer 再發到各個平台 |

不確定有沒有 API？直接問你的 AI：這個服務有官方 API 嗎？要申請什麼權限？一天能用幾次？它查得到文件，答完再對照官方文件，對得上就照著接。

實務上兩種常常一起用。先讓 computer use 跑一次，確認流程走得通；要變成每天跑的工作，再改成 API。

真的拿不定主意，就問自己三題：

1. 這件事一個月要做幾次？
2. 做錯了誰會發現、多久才發現？
3. 對方有沒有 API 或 MCP？

前兩題的答案越大，就越該接 API。

**記住這句就好：** 有 API 就用 API；沒有，或只做一兩次，才讓 AI 去點。

## AI 做判斷，系統做執行

AI 自己就會變，怎麼跟要求穩定的 API 一起用？

AI 本身就是非確定性的。同一個問題問兩次，它的回答常常不一樣。所以比較好的分工是：讓 AI 做判斷，讓確定性系統做執行。

| | 交給誰 | 例子 |
| --- | --- | --- |
| 判斷 | AI | 要發什麼、什麼時候發、這篇寫得好不好 |
| 執行 | API | 把文章送出去 |

判斷的部分錯了，你看得出來、改得掉；執行的部分每天要跑幾百次，就要每次都一樣。兩種東西各放在適合的位置。

AI 怎麼用 API？你的 AI 本來就會呼叫工具。你給它一個發文工具，它想好內容，就填好欄位叫這個工具，工具再去呼叫 Threads 的 API。

系列上一篇講過，工程師會把做得穩的流程收進黑盒子。API 就是別人收好的黑盒子，你照規格丟東西進去，結果就出來。

## MCP：給 AI 用的 API

最近一直聽到 MCP，它跟 API 是什麼關係？

官方的說法是，MCP 是一個把 AI 應用接上外部系統的開放標準，官網把它比喻成 AI 的 USB-C 接頭。以前每個 AI 工具要接 Google 行事曆、接 Notion，都要各寫一套。有了 MCP，服務那邊照標準開一次，Claude、ChatGPT、Cursor 這些 AI 工具都能接。

它背後一樣是 API，只是多包了一層寫給 AI 看的說明：有哪些工具、每個工具要填什麼。

| | 一般 API | MCP |
| --- | --- | --- |
| 誰決定用哪個 | 工程師先把步驟寫死 | AI 自己讀說明，自己挑工具 |
| 共同點 | 照規格講話 | 照規格講話 |

### 小屋的 MCP

我叫 bot 用 teach 解釋小屋的 MCP。它拿住民收信這件事舉例：

1. 信先進住民的信箱。
2. 小屋去叫醒 bot。
3. bot 用看信箱的工具讀信，用簽收的工具回報收到了。

它還翻出來，MCP 那扇門後面，接的其實是小屋本來的內部 API。

小屋的 MCP 開在 `/mcp`，清單上有 16 個主要工具，像入住、看信箱、簽收、寄出。住民的 bot 連進小屋收信、回覆、更新任務狀態，走的都是這些工具。

### CLI 還是 MCP

之前有一陣子，網路上有人喊 MCP 已死，叫 AI 直接用 CLI 命令列就好。我看了就笑笑。最近 MCP 又熱起來了。

從個人的角度，CLI 確實比較方便：裝好就能用，AI 也很會打指令。換成一個團隊、很多人一起用，每個人都要自己找有哪些工具、自己裝、自己設定，這些探索跟部署的摩擦加起來，就把 CLI 的方便抵銷了。MCP 是服務那邊開一次，大家連上去，看到的就是同一份工具清單。

### API 要切多大

MCP 有個麻煩，其實是 API 的老問題。當年碰 APIM，最常討論的就是 API 要切多大。

| 切法 | 好處 | 麻煩 |
| --- | --- | --- |
| 切得大 | 一支做完一整件事，叫起來方便 | 彈性低，想換個做法就得等對方再開一支 |
| 切得小 | 什麼都組得出來 | 支數一多就難管，一件事要來回呼叫好幾趟，每一趟都是延遲 |

GraphQL 是一種折衷：只開一個入口，要哪些欄位由呼叫的人自己挑，一次拿齊。

MCP 的麻煩就在這裡：工具切太細，清單長到 AI 看不完，每叫一次還要等模型想一輪。

小屋自己也撞過這題。工具一路加，清單越拉越長，10 月我把主要工具縮回前面看到的 16 個；外觀、家具這些比較少用的，改成兩步：先查有哪些操作，再挑一個執行。一次只做一件事，也不准跑腳本。

Cloudflare 的 Code Mode 做法很像，也只給 AI 兩個工具，一個查、一個執行。差別在執行那一步：它收的是 AI 自己寫的一段程式，可以把好幾支 API 串起來，一次跑完，只把結果拿回來。Cloudflare 自己有 2,500 多支 API，這樣只要大約 1,000 個 token 就講得完。

讓 AI 跑自己寫的程式，就得找個關得住的地方。Cloudflare 用的是 Dynamic Workers，今年 3 月開放測試：臨時開一個隔離的小沙盒，幾毫秒就開好，官方說比開容器快大約 100 倍；沙盒可以設成連不上網路，你給它哪些 API，它就只能叫那些。

### 四種做法怎麼選

看到一個服務有 MCP，就把它當成給 AI 用的 API。把 CLI、MCP 也算進來，就沒有絕對的路，要綜合考量：

| 情況 | 選 |
| --- | --- |
| 自己一個人用 | CLI 最順手 |
| 團隊很多人一起用 | MCP 省下的摩擦最多 |
| 要每天穩穩地跑 | API |
| 對方什麼都沒開 | 才讓 computer use 去點 |

## 小屋怎麼接外部服務

小屋怎麼接 Google 行事曆跟 Notion？我叫 bot 跑了一次 teach，問它：是走 API，還是叫 AI 去開網頁點？

### Google 行事曆

它翻了小屋的文件：行事曆走的是 Google 官方的 API。

1. 老闆按一次同意。
2. Google 發一把 key 給小屋，權限只有讀取自己的行程（`calendar.events.owned.readonly`）。
3. 小屋拿這把 key 去問未來 30 天的行程，一次最多 100 筆，回來的是格式固定的資料。

Google 那邊有變動，會主動通知小屋去更新；小屋也每 6 小時自己對一次帳，因為通知有時候會掉。這就是確定性系統的寫法：照規格接，再補一道保險。

這種有變動就通知你的做法，就是前面提到的 webhook。之前講事件那篇提過，有事才按門鈴，比每隔幾分鐘去敲門問一次省很多。

### Notion

Notion 也一樣，是用 Notion 發給你的 key 去讀頁面，Notion 把它叫 integration token。這些 key 存進小屋之前都會先加密，就算資料被拿走，也讀不出來。

### 小屋開瀏覽器的唯一場合

小屋裡其實也有會開瀏覽器自動點的程式，叫驗收腳本。它在工程師自己的電腦上開一間假的小屋，再開一個看不見的 Chrome 照劇本點，確認畫面跟按鈕沒壞。開網頁點，小屋拿來做測試。

這段也是叫 bot 用 teach 問出來的。它還指出，這支腳本會把連到小屋以外的請求全部擋掉，正式上線的小屋裡也根本沒有瀏覽器。理由很實際：

1. 網頁一改版就點不到。
2. 要點別人的網頁，就得拿帳號密碼去登入。

接別人的服務、每天幫很多間店同步資料，這種量跟穩定度，小屋全部交給 API。

## 濫用與管理

API 好用，key 管不好，出事也很快。用 vibe coding 寫程式的新手，很容易踩的雷都在管理這一塊。分兩邊講：你去用別人的 API，跟你提供 API 給別人。

### 用別人的 API

**雷 1：key 外流。** AI 幫你寫程式時，很常把 key 直接寫進程式碼；你一推上公開的 GitHub，網路上專門掃 key 的機器人常常幾分鐘內就撿走，接著用你的額度、刷你的帳單。已經推上去的 key，就當它外流了，直接作廢換新。

**雷 2：key 放在網頁前端。** 瀏覽器裡的程式碼誰都看得到。前面按 F12 看過，網頁送出去的每一個請求都攤在那裡。key 要放在後端，也就是你自己架在伺服器上的那一段，網頁只呼叫你自己的後端，由後端拿 key 去接別人的 API。

**雷 3：沒設上限。** 很多平台可以設每天的用量上限或預算警示，就算 key 被偷，或 AI 寫出一直重打的迴圈，損失也有個底。懷疑外流就馬上作廢，換一把新的，這叫 rotate。

### 提供 API 給別人

你開了 API，就要管誰能接、能做什麼：

- **發 key**：每個接的人發一把自己的 key。
- **分權限**：照 scope，也就是權限範圍分開，有的只能讀，有的可以寫。
- **限流**：也就是 rate limit，每把 key 一分鐘最多呼叫幾次，超過就回 429 這類錯誤代碼。前面講的 Threads 也有類似的上限，一個帳號一天最多發 250 篇；發太快、太多，平台也可能把你當成垃圾帳號。
- **留紀錄**：每一次呼叫是哪把 key、什麼時候、做了什麼，都記下來。出事的時候，才查得到是誰、從哪裡開始。

誰能接、能接多少、出事查得到，這三件事，就是我當年碰的 APIM 在管的。

### 小屋怎麼做

我叫 bot 用 teach 問了一次：

| 做法 | 小屋的設計 |
| --- | --- |
| key 的壽命 | 發給住民 bot 的 key 叫通行證，8 小時就過期，要拿 30 天的續約單去換新 |
| 存放 | 小屋只存 key 的指紋，資料庫被偷了也拿不到能用的 key |
| 限流 | 每把 key 每分鐘 300 次，超過就回 429 |
| 被盜偵測 | 同一張續約單被用了第二次，小屋就當它被偷，整組作廢 |

**這段帶走一句：** 用別人的 API，key 不進程式碼、不放前端、權限開最小、設上限；提供 API，就發 key、分權限、限流、留紀錄。

## 跟著老闆走一遍

最後用一個假設的情境走一遍。人蔘當咖啡店老闆，AI 叫和真。老闆想要每天早上自動發一篇今日特調到 Threads。

| 步驟 | 發生什麼事 |
| --- | --- |
| 1. 先用 computer use | 和真先開瀏覽器，照著老闆的意思發了一篇「今日特調：桂花拿鐵」。老闆看了一下，內容跟排版都對，流程走得通。 |
| 2. 建議改 API | 和真說：如果要每天發，建議改走 Threads API。要先建一個 Meta 應用程式，拿一把 key，這一步要老闆自己登入授權。 |
| 3. 存 key | 老闆授權完，和真把 key 放進 secrets。程式碼裡只寫這把 key 的名字 `THREADS_ACCESS_TOKEN`，看不到內容。 |
| 4. 排程 | 和真寫了一個每天早上 8 點跑的排程：自己想今天的文案，再呼叫 API 發出去。發完回一句：今天的特調發好了，附上文章連結。 |
| 5. 出錯 | 有一天，老闆在 Threads 的設定裡把授權關掉了。隔天早上 API 回了一個權限錯誤，和真看得懂這個代碼，馬上回報：授權被關掉了，要重新授權才能發。 |
| 6. 續期 | 60 天後 key 快過期，和真提前提醒老闆續期。 |

這種事 API 會照規格告訴你，用不著等哪天突然發不出去才發現。

## 回家問你的 bot

這週可以做一件事：挑一個你常用的服務，Threads、Google 表單、你的記帳 app 都可以，問你的 AI：它有沒有官方 API？要申請什麼？一天能用幾次？

裝了 pstack 的話，就用 teach 問：如果我想自動做這件事，用 API 跟用 computer use 各要怎麼做？各有什麼風險？叫它拿你的專案舉例。

叫它把兩種做法的步驟列出來，你就會看到差別：一邊是申請權限、拿 key、照規格送；一邊是截圖、點擊、再截圖確認。

### poteto-mode

除了 teach，pstack 還有一個平常做事的入口，叫 poteto-mode。想學就用 teach；要動手做，就打斜線 `poteto-mode` 開頭，再講你要做什麼。它會先判斷這是哪一種工作：

| 你的情況 | 它走哪條路 |
| --- | --- |
| 想搞懂 | 調查 |
| 東西壞了 | 修 bug |
| 要加功能 | 新功能 |
| 還沒想清楚 | 先做個原型試試 |

每一條都有自己的步驟；修 bug、加功能這種動手的，做完會先在真的環境驗證過，再回報給你。

### 讓 computer use 試之前

先開一個測試帳號，或用一台沒有登入重要帳號的電腦。官方文件也這樣建議：別讓它碰到敏感的帳號資料，重要的按鈕留給你自己按。

### 三句口訣

叫 AI 幫你接服務的時候，在需求後面加這三句：

```
用官方 API
key 放 .env，不寫進程式碼
只申請用得到的權限
```

## 先點得通，再接 API

回到開頭：為什麼寫程式一定要懂 API？因為你的程式、你的 AI 要跟外面的世界講話，靠的就是它。

computer use 讓 AI 什麼都能試；API 讓試成功的事情每天穩穩地跑。先點得通，再接 API。口訣記得帶走：官方 API、key 放 .env、權限開最小。

環境跟持續整合，就是程式從你的電腦一路走到正式站的那段，之後會開一集講。

你最想讓 AI 幫你自動做的是哪件事？到影片底下留言告訴我，我們一起看它有沒有 API。想讓自己的 AI 有個家，可以來 PA Cafe 免費開一間小屋。
